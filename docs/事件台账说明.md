---

## 一、它解决什么问题

前面几轮反复遇到同一个尴尬：**所有结论都无法回测。**

- `policy_radar` 的事件取自滚动新闻，免费接口历史只有几小时
- `policy_calendar` 的事件日期确定，但只往**未来**展开
- 于是"这套东西到底有没有用"这个问题，一直没有数据能回答

**台账就是为这个问题存的：** 它把事件**先记下来**，然后持续回填"之后市场/个股实际怎么走了"。
攒够样本之后，才有资格谈有没有用 —— 在此之前任何结论都不成立。

## 二、为什么必须独立持久化

```
alerts.jsonl 只保留 7 天（alert_store.MAX_DAYS = 7）
```

事件 7 天后就被清掉，而 T10 需要 10 个交易日。**光靠 alerts 永远攒不出完整样本。**
所以台账独立存在 `databridge\data\event_ledger.json`，不随 alerts 清理。

## 三、口径设计（这几条决定了数字可信不可信）

### 1. 基准 = 事件日**前一交易日**收盘

```
T0 = 事件日收盘 / 前一日收盘 - 1     ← 当日反应
TN = 之后第 N 个交易日收盘 / 前一日收盘 - 1   ← 累计
```

不用事件日收盘做基准，是因为事件当天的价格可能**还在反应中**，用前收更干净。

### 2. 必须记超额

个股涨了 3%，但大盘涨了 5%，超额是 **-2%**。不记基准就等于自欺欺人。

```
excess = stock_ret - bench_ret
```

### 3. 基准用**全市场涨跌幅中位数（等权）**

不用指数。原因见下节 —— 指数会被权重股拉动，等权中位数才代表"多数股票"。

### 4. 复权口径

跨期收益用**前复权** `close`（数据湖里 `close == raw_close`，ratio=1，即当前无除权影响）。
除权日不会产生假跳空。

## 四、实测中发现的两个数据陷阱（**重要**）

### 陷阱 1：系统 overview 的涨跌家数是**盘中快照**，不是收盘

我一开始拿 `/api/overview/market` 的 breadth 去核对基准，发现矛盾：

| 来源 | 2026-11-04 涨跌家数 | 中位涨跌 |
|---|---|---|
| 系统 overview | up 1665 / down 3746 | -0.69% |
| **数据湖自算** | **up 4666 / down 778** | **+1.88%** |

查 `quote_status` 才发现：`market_phase: "morning_final", is_trading_hours: false`
—— **那是上午收盘的快照，不是全天收盘。**

数据湖的日K 才是真实收盘：**小盘普涨（中位 +1.88%），但权重股跌**，
所以指数看着平，中位数却是正的。这正是"用等权中位数而非指数"的理由。

**结论：台账的基准一律用数据湖自算，不取 overview。**

### 陷阱 2：ETF 日K 比股票滞后一天

实测 2026-11-04：股票分区有、ETF 分区**最新只到 11-03**。
原先这种事件会落进含糊的 `waiting`，分不清是"没到日期"还是"没数据"。

现在给出明确状态 `waiting_price` 和原因：

```
159682.SZ 创业板50ETF景顺: ETF 日K 尚未同步 2026-11-04（该股最新 2026-11-03）
```

## 五、样本从哪来（解决了"要等几个月"的难题）

光从 alerts 摄入，只能拿到**从今天往后**的事件，样本要攒几个月。

所以加了 `--seed-calendar N`：**从政策日历导入过去 N 个月已发生的周期事件**。

**这里踩了一个坑**：`load_calendar` 的展开窗口是从 asof 的**上个月往后**推，
用 `today` 作为 asof 时，过去的事件根本不会生成 —— 实测只导入 5 条。
改成以 `lo`（N 个月前）为 asof、窗口向后开，才正确导入 **23 条**。

### 另一个坑：同一次发布不能算两个样本

CPI/PPI 的窗口是 `[9, 10]` 两天，会各生成一条。若都当独立事件，
**同一次发布被重复计入**，污染统计。实测清理掉 4 条重复（6/7/9/10 月）。

修法：按「周期 id + 年月」归并，只留该月最早那条。

**⚠ 这组数字不能当结论，三个理由：**

1. **样本量 <30**（程序会自动打印警告，不靠人记得）
2. **时间区间只有 6 个月**（2026-05 ~ 11），且这段是全市场调整期，

这与该区间的整体弱势一致 —— **不能推断因果关系。**

## 八、限制（**必读**）

| 限制 | 说明 |
|---|---|
| **样本远不够** | 个股事件 0 条可用，市场级 27 条；两者都 <30 |
| **区间太短且单边** | 只有 6 个月，且是调整期，事件后下跌很可能只是市场在跌 |
| **方向是模型判定** | `event_direction` 来自 AI，不是事实；判错则对照跟着歪 |
| **日历事件无方向** | 市场级样本只能看"市场涨跌"，不能验证方向判定 |
| **ETF 有滞后** | ETF 日K 常比股票晚一天，状态会是 `waiting_price` |
| **只记录，不做检验** | 没有任何显著性检验、没有 p 值、没有"能否交易"的结论 |
| **`--seed-calendar` 有前视风险** | 导的是**已发生**事件，回填当然完整；但这只用于补样本，不可用来"预测" |

## 九、这个模块的正当用途

**唯一正当用途：积累证据。**

- ✅ 攒到 100+ 条个股事件、跨 2 年以上后，回来看"判定为利好的事件后续是否真的跑赢"
- ✅ 发现某类事件系统性失效（如"减持公告"从来不影响走势）→ 据此**减少告警噪音**
- ❌ **不能**现在就拿 B 节数字做决策
- ❌ **不能**把"事件后下跌"解读成"事件是利空"
