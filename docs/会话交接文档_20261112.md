用户报 token `tsp_6013f1...0135` 无法调用，且**内网地址返回 401**。

排查结论：**token 与 scope 全程正常**。

| 检查 | 结果 |
|---|---|
| token 归属 | sha256 命中 `tok_147d15e0` / `external-api-v2`，`revoked: false`，6 个 scope 全有 |
| 字串合法性 | 长度 68（4+64）、前缀 `tsp_`、正文 64 位全小写 hex、无空白/大写/不可见字符 |
| 实测调用 | `/api/watchlist`、`/api/alerts/summary`、`/api/risk/positions` **全部 200**（本机与 `192.168.31.46` 均 200） |
| 网络门禁 | `API_TOKEN_LOCAL_ONLY` 默认 1 → 公网 403；该门禁**在 v0.3.30 就已存在**（用户自己的提交 `88956ebb`） |

**真因**：`app\main.py:646-647` 原为 `if authz.startswith("Bearer ")`，
对**方案名大小写敏感**。非标准写法整条掉进密码会话分支，返回
`401 {"detail":"未登录或会话已过期"}`——错误信息指向"没登录"，把真实原因完全掩盖。

7 种写法实测（修复前）：

| 写法 | 结果 |
|---|---|
| `Bearer tsp_...` | 200 |
| `bearer` / `BEARER` / `BeArEr` | **401 未登录或会话已过期** |
| 无前缀只给 token | 401 |
| `Bearer` 后无空格 | 401 |
| 值被加引号 | 401 |
| `Bearer` 后双空格 | 200（多余空格被 `.strip()` 吃掉） |

**修复**（依据 RFC 7235 §2.1：auth-scheme 是 case-insensitive）：

```python
scheme, _, token_part = authz.partition(" ")
token_plain = token_part.strip()
if scheme.lower() == "bearer" and token_plain:
```

**安全边界不放宽**：无方案名、`Basic` 等错方案仍走会话分支返回 401。

修复后实机复验：`Bearer`/`bearer`/`BEARER`/`BeArEr`/多空格 **全部 200**；
`Basic <token>`、裸 token → 401 未登录；格式对但值错 → 401「API Token 无效或已吊销」（提示准确）。

## 三、本会话确认的真 bug（按严重度）

### 🔴 BUG 1：配置备份/资源导入会损坏 CRLF 文件（Windows 数据损坏）

**位置**：`backend\app\services\fs_utils.py::atomic_write_text`、
`backend\app\services\config_backup.py::_write_payload`

**机理**：`tmp.write_text(text, encoding="utf-8")` 用默认换行模式，Windows 上把文本里
已有的 `\r\n` 再翻译一次 → `\r\r\n`；读回时通用换行又把 `\r\r\n` 解释成两个换行，
**每往返一次多一个空行，`\r` 会累积**。

**触发链**：`POST /resources/apply` → `resource_bundle.apply_resources`
→ `config_backup._write_payload`（对 `.py/.json/.yaml/.js` 等先 decode 再走 atomic_write_text）。

**实测证据**：
- `test_minute_price_volume_strategy.py` 断言 `imported.read_bytes() == STRATEGY_PATH.read_bytes()`
  得 `b'...\r\r\n' != b'...\r\n'`
- `test_config_backup.py` 读回多出两个空行

**影响面**：配置备份恢复、资源导入、扩展安装，凡是 CRLF 源文件必坏。

**修复**：`atomic_write_text` 加 `newline=""`；`_write_payload` 改为**先校验可解码、
再写原始字节**（解码只做校验，不做中转）。

### 🟠 BUG 2：空的分钟数据目录被当成「查询失败」

**位置**：`backend\app\tickflow\repository.py`

两个问题叠加：

1. polars 对「glob 展开为空」**抛 `ComputeError`** 而不是返回空帧。`kline_etf_minute`
   建了目录但零个 parquet（实测 `entries=False`），于是每次查询都抛异常打一条 WARNING。
   而"这类资产还没有分钟数据"本是正常状态。真实运行日志里每天刷 3 条：
   ```
   分钟K查询失败: failed to retrieve first file schema (parquet): expanded paths were empty
   ```
2. **更隐蔽**：`_minute_partition_path` 用 `rsplit("/")` 从 glob 反推根目录，
   但 glob 在 Windows 上是反斜杠 → 拼出 `...\part.parquet/date=...` 这种不存在的路径，
   **当日分区永远判为缺失**，退化成全树扫描（或连已有数据都读不到）。

**修复**：新增 `_minute_base_dir()`（用 pathlib `parents[1]` 逐级回退，两种分隔符都对）、
`_minute_dir_has_entries()`（廉价探目录）、`_minute_scan_target()`（空目录短路）。
`get_minute` / `get_minute_batch` / `get_minute_range` 三处统一走它。

**实测验证**（真实数据目录）：
```
etf   base=...\kline_etf_minute exists=True entries=False → scan_target=None → rows=0（零告警）
stock base=...\kline_minute    exists=True entries=True  → 正常读取
```

### 🟠 BUG 3：代理环境变量只在一个入口被清洗

**位置**：清洗逻辑原本**只写在 `run-local.py`** 启动脚本里。

**机理**：`no_proxy` 含 `[::1]` 时 httpx 抛 `InvalidURL: Invalid port: ':1]'`。
`pytest`、`uvicorn app.main:app` 直起、Docker 等入口全部中招。

**它曾造成真实故障**：11-09 实时行情连续失败 → 系统自动把
`realtime_quotes_enabled` 降级成 `False`（我排查后手动恢复为 `true`）。

**修复**：把清洗挪到 `backend\app\__init__.py`（包导入最早阶段），幂等，
已干净的值原样不动、不覆盖用户其它条目。

### 🟡 BUG 4：策略文件不认 PEP 263 编码声明

**位置**：`backend\app\strategy\engine.py::_load_file`（及 `_read_source` 调用方两处）

**机理**：一律 `read_text(encoding="utf-8")`。带 `# -*- coding: gbk -*-` 的**合法**
Python 策略会被 `UnicodeDecodeError` → 包成 `ValueError("策略安全校验失败")` → 加载不了。
（fail-closed 本身是有意的，问题在解码口径。）

**修复**：改用 `tokenize.open(path)`（标准库答案：检测 BOM + 前两行 coding 声明，
缺省 utf-8，与 CPython 导入行为一致）。无声明时行为逐字节不变。

## 九、本会话的方法论教训

1. **"测试通过"可能是假通过**。`test_instruments_retry` 初版把 `_run_tracked` stub 成从不调用 `fn`，
   于是 `TypeError: unexpected keyword argument 'on_progress'` 这个真 bug 完全抓不到，
   直到真机实跑才炸出来。**反证必须做到位**：改坏实现 → 测试必须失败。

2. **反证也要验证自己**。第 3 项修复的反证第一版用 monkeypatch 替换了*被测函数本身*，
   所以"4 个测试全过"是假的；改成 patch 函数内部真正调用的入口（`policy._detect_tickflow_caps`）
   才暴露出失败。

3. **失败数变少不等于没问题**。全量 145→27 的下降里，有一大半是测试自身缺陷
   （中文 Windows 的 GBK 默认编码、`zipfile` 在 Windows 归一化反斜杠），
   不是产品修好了。必须逐条判定"是产品缺陷、测试缺陷，还是环境限制"。

4. **日志里的日志不一定是真的**。`backend.log` 混了 pytest 的输出，
   排查时差点把测试的 `ETF(0/10)` 当成生产异常。

5. **调度时刻要对着数据源的发布节奏核**。15:35 这个默认值对免费档是错的，
   而它的注释写着"留 5 分钟缓冲"——**注释里的假设也要验证**。
