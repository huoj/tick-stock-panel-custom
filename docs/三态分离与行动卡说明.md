# 自选 / 计划 / 持仓 三态分离 与 行动卡

> 起因：用户 2026-11-13 的两条要求
> 1. 自选列表不等于投资组合。要能记录持仓数量、成本、买入时间、计划持有期和可接受亏损，
>    并把「自选观察 / 实际持仓 / 计划买入」分开展示。
> 2. 每只股票给一张简单的「行动卡」，快速回答四个问题，并把
>    **事实、系统推断、用户计划** 明显区分，不能只给一个买入/卖出分数。

---

## 一、三态分离：同一标的只能属于一种状态

| 状态 | 内部值 | 什么情况 | 计入盈亏 | 参与权重 |
|---|---|---|---|---|
| 自选观察 | `watch` | 只放进自选，没有钱在里面 | ❌ | ❌ |
| 计划买入 | `planning` | 填了分批价格/资金安排，但**一股没买** | ❌ | ❌ |
| 实际持仓 | `holding` | paper 台账里有真实成交 | ✅ | ✅ |

### 状态判定优先级

```
holding  >  planning  >  watch
```

**持仓优先于计划** —— 已成交的计划不再是计划。否则同一只票会出现
「既算持仓又算计划」的双重身份，正是用户担心的「把提示误认为已持仓」。

**总闸门**：`GET /api/position-plans/classify/{symbols}` 对每个标的返回
`counts_toward_pnl`，前端据此决定要不要显示盈亏。只有 `holding` 是 `true`。

### 为什么必须分开（来自 `portfolio_positions.py` 的既有结论）

自选清单可以随手塞几十只票，把等权当成组合会算出「行业很分散、回撤可控」
这种**看起来像结论的东西** —— 那是清单的性质，不是持仓的性质。

### 数据来源

| 状态 | 数据源 | 模块 |
|---|---|---|
| 实际持仓 | `data/paper/accounts/<acc>/` 台账重放 | `services/portfolio_positions.py`（既有，复用） |
| 计划买入 | `data/user_data/position_plans/plan_<symbol>.json` | `services/position_plan.py`（新增） |
| 自选观察 | `watchlist.parquet` | `services/watchlist.py`（既有，复用） |

### 手工录入真实持仓（P0 补充：不玩模拟盘也能做组合分析）

**问题**：上面「实际持仓」的唯一来源是 paper 台账（`data/paper/accounts/<acc>/`）。
不玩模拟盘、也不接券商接口的人，永远拿不到真实权重 —— 三态里只会是「自选观察」，
组合风险面板和持仓段全部算不出来。

**做法**：新增一个不依赖任何外部账户的手工录入口径，只收三件事 —— 数量、成本、建仓日。
**不接受亏损与计划持有期不在这里填**（那是用户意图，归「买入计划」管，一处一个来源）。

| 项 | 内容 |
|---|---|
| 存储 | `data/user_data/manual_holdings/holding_<symbol>.json`；账户现金 `account.json` |
| 服务 | `services/manual_holdings.py`：存储（upsert 保留 `created_at`）、校验、账户权益 |
| 口径接入 | `portfolio_positions.load_actual_positions(..., source="manual")` 新增 `MANUAL_BASIS`；`source="auto"` 时若已录入手工持仓则优先用它（并提示未用模拟盘） |
| 端点 | `GET/PUT/DELETE /api/manual-holdings/{symbol}`、`GET/PUT /api/manual-holdings/account` |
| 前端 | 持仓总览页顶部「我的真实持仓」面板（录入 + 明细 + 现金） |

**三条诚实边界（写进了模块 docstring 和 API limitation，不在 UI 里遮掩）**：

1. **不假装与券商对账过** —— 成本按你填的数字算，分红送股、手续费、部分成交都不还原。
2. **现金要么录、要么说明** —— 没录现金时权重分母 = 持仓市值，权重合计会等于 1（看起来像满仓），
   面板会写明「若你还有现金或其它资产没录，实际仓位比这里显示的更低」。
3. **不做 T+1 / 可用量推断** —— 没有流水，所以 `available_qty` 恒为 `null`，界面不显示「可用」。

**未对账**是显式标注在 limitation 里的（不是隐藏假设）。

**价格口径**：手工持仓的现价按各标的最近一根日线收盘价估值（`price_source="daily"`）；
盘中实时价需由调用方传入 `price_map` 才标 `live`；取不到任何行情时标 `cost`（此时盈亏恒为 0，
界面会写「按成本（盈亏不可信）」）。

**三态分类的判定会跟随这个口径**：录入后 `GET /api/position-plans/classify/000333.SZ` 会从 `watch`
变成 `holding`、`counts_toward_pnl=true`，行动卡持仓段与 `/api/risk/portfolio` 的权重同时生效。

## 二、计划买入：记录但不参与会计

### 字段

| 字段 | 说明 |
|---|---|
| `planned_hold_days` | 计划持有天数（1~3650）。到期时提醒重新评估，**不是自动卖出** |
| `acceptable_loss_pct` | 可接受亏损百分比（0~100，不含 0）。用于换算成具体的**亏损纪律线** |
| `batches[]` | 分批计划：`price` + `amount` + `label` + `done` |
| `note` | 自由备注 |

### 校验是 fail-closed 的

非法值直接 400，**不静默修正**：

- `planned_hold_days` 必须是 1~3650 的整数
- `acceptable_loss_pct` 必须在 (0, 100]
- `batches[].price` 必须 > 0
- `batches[].amount` 不能为负

### 兑现度对照（只陈述事实，不给建议）

`assess_plan(plan, current_price)` 产出：

**事实**
- 计划 N 批 / 已执行 M 批 / 剩余多少元
- 计划加权均价 vs 现价的偏离百分比
- 有几批计划价低于现价（等回调才成交）
- 可接受亏损与计划持有期

**需要注意**
- 计划里没有任何分批价格 → 「这只是一条备注，不是买入计划」
- 未设可接受亏损 → 「无法判断何时该认错」
- 未设计划持有期 → 「无法判断是短炒还是长持」
- 有批次计划价已高于现价 → 「若已错过，需重新评估计划」

**刻意不产出「该不该买」** —— 那是用户的决定，系统只把差距摆出来。

## 三、行动卡：三段式 + 四个问题

### 端点

```
GET  /api/action-card/{symbol}              行动卡（三段 + 四问）
GET  /api/action-card/{symbol}/diagnosis    只出诊断原始数据，供高级用户自判
GET  /api/position-plans                    全部计划
GET  /api/position-plans/{symbol}           单个计划
PUT  /api/position-plans/{symbol}           新建/更新计划
DELETE /api/position-plans/{symbol}         删除计划
GET  /api/position-plans/{symbol}/progress  计划 vs 现价对照
GET  /api/position-plans/classify/{symbols} 三态分类（防误认总闸门）
```

### 三段的分工（这是行动卡存在的理由）

| 段 | 内容 | 权威性 | 前端颜色 |
|---|---|---|---|
| `facts` | 价格、均线、量比、RSI、ATR、筹码、持仓成本与浮盈亏 | 系统直接测得，**不解释** | 中性灰 |
| `inference` | 强弱判定 + 证据、同形态统计 + 基准、置信度 | 有前提、有样本量，**可被推翻** | 强调色 |
| `user_plan` | 成本、期限、亏损容忍、分批计划、兑现度 | **用户权威**，系统只做对照 | 警告色 |

**核心禁令：绝不合并成一个买入/卖出分数。**
分数不可解释、无法追溯、掩盖分歧。测试里用 `test_action_card_never_returns_a_buy_sell_score`
直接断言响应中不存在 `buy_score` / `sell_score` / `recommendation` / `rating` / `signal_score`。

### 四个问题

#### 1. 偏强 / 偏弱 / 方向不明

**不是加权评分，是证据投票** —— 每条理由都能独立核对：

| 维度 | 判据 |
|---|---|
| 结构 | 价 vs MA20/MA60/MA120 的排列 |
| 动能 | MACD 柱正负 + 扩张/收敛 |
| RSI | ≥70 超买 / ≤30 超卖 / 中性 |
| 量价配合 | 放量涨 / 缩量涨 / 缩量跌 / 放量跌（**缩量跌 ≠ 缩量涨**）|
| 收盘位置 | ≥80% 承接到底 / ≤20% 承接不足 |
| 位置 | 250 日区间分位 |
| 头顶筹码 | 上方套牢盘占该方向总量 ≥25% |

净票差 ≥+2 → 偏强；≤−2 → 偏弱；否则方向不明。

**量价组合的判读是这套卡最关键的一条**：

- 缩量上涨 = 卖的人走了（下跌末端可靠、高位不可靠）
- **缩量下跌 = 买的人不见了**（性质完全不同，往往还要跌）
- 放量上涨 = 买的人来了（需次日接力）
- 放量下跌 = 抛压沉重

#### 2. 持有时，什么情况说明原判断可能错了

三类来源，按优先级：

1. **用户设的可接受亏损**（`critical`）—— 唯一「必须遵守」的一条，换算成具体价位
   `成本 × (1 − 亏损%)`。没设置时必须警告，**不编默认值**。
2. **技术结构位**（`critical`/`warning`）—— MA60 下方 / 跌破 MA10 / 跌破近 20 日低点
3. **计划持有期到期**（`warning`）—— 到了原定时间框架，无论盈亏都该重评（不是自动卖出）

#### 3. 没买时，哪些条件出现后再考虑

**只给条件，不给建议**。每条带价位与可验证特征：

| 类型 | 条件 |
|---|---|
| `breakout` | 放量突破近 20 日高点（量 > 1.5 倍均量）|
| `pullback` | 上升趋势中回踩 MA60 不破（止损距离最短）|
| `volume` | **下降趋势中只在放量止跌时谈条件**，缩量阴跌不构成条件 |
| `valuation` | RSI 未到超卖区时，明确说「缺乏反弹动能」|

如果结构与量能都没给信号，输出「当前没有可操作的入场条件 —— 此时进场等同于猜方向」。

#### 4. 必须核对的事实

这些是**系统给不了答案**的，只能告诉用户去看什么、在哪看：

- 最近一期财报的营收/利润同比（技术面无法区分「杀估值」与「杀业绩」）
- 业绩预告/快报及披露期
- 大额解禁、减持、质押公告
- 所属行业景气度与产品价格趋势
- 低位时追加：机构调研/评级变化

每项带 `where`（去哪查）与 `status`（`unverified` / `unavailable`）。

## 四、代码结构

### 单一实现，两个消费方

```
app/services/stock_diagnostics.py    ← 算法唯一实现（K线/趋势/指标/筹码/同形态/强弱）
   ├─ scripts/analyze_stock.py       ← 命令行（只读数据、渲染文本）
   └─ app/services/action_card.py    ← 行动卡（事实段 + 推断段）
```

**为什么不放进 `indicators/pipeline.py`**：那是全市场批量物化列（逐日重算、落盘、
供策略消费）；这里是单标的按需诊断（读 300 根日线现算、不落盘、供人读）。
精度要求相同，成本模型完全不同。

### 口径红线（写在模块 docstring 里）

- 所有指标都是收盘价（前复权）口径，与策略/enriched 一致
- 同形态统计**必须按当日实际涨跌方向匹配** —— 写死「上涨+缩量」会拿「涨」的历史
  去预测一只「跌」的票，结论完全反掉（实测：宏柏新材 3 日胜率从 53% 变 42%）
- 胜率**必须与无条件基准一起给** —— 没有基准的胜率是骗人的
- 样本 < 30 必须显式警告

## 五、前端

页面：`frontend/src/custom/action-card/`（自动发现于 `src/custom/*/extension.tsx`）

- 状态徽标三色区分（灰 / 黄 / 紫）
- 三段各自独立的彩色边框与图标（事实=灰勾、推断=蓝信息、计划=黄警告）
- 计划编辑弹窗顶部明确写「计划只是记录，不会产生任何订单，也不计入盈亏」
- 空持仓时「持有时什么算错了」显示「没有持仓，无从谈原判断」，而不是空列表

Query key 带 symbol（`QK.actionCard(symbol)`），切换标的不会读到上一只的缓存。

### 组合风控页（`/portfolio-risk`）

`frontend/src/custom/action-card/PortfolioRisk.tsx`，导航项「组合风控」。
顶部固定放「我的真实持仓」录入面板（真仓口径的唯一数据来源），下面把**两种口径分开算**：

| 口径 | 后端调用 | 权重含义 | 是否计入盈亏 |
|---|---|---|---|
| 真实持仓（手工录入） | `GET /api/risk/portfolio?source=manual` + `POST /api/risk/buy-simulation` 带 `source=manual` | 持仓市值 /（现金 + 持仓市值），不归一化 | 是 |
| 自选观察（导入自选） | `POST /api/risk/portfolio` 带等权 `holdings` | 每只 `1/n` 的等权假设 | 否（界面显著标注「自选 ≠ 持仓」） |

- 「导入自选」按钮调 `api.watchlistList()`，去重后一次最多带 100 只（相关性矩阵 O(n²)），超出如实截断提示。
- `PortfolioRiskPanel` / `BuySimulationCard` 新增 `manual` 开关：`manual && !account` 时走手工真仓口径；`account` 优先，保持模拟盘页既有挂载点行为不变。
- 修掉一个刷新 bug：`ManualHoldingsPanel.refresh()` 原来 `invalidateQueries(['portfolio-risk'])` 匹配不到面板的 key（前缀是 `QK.customSignals`），已改为 `[...QK.customSignals, 'portfolio-risk']`。
- 3018 端口服务的是 `frontend/dist` 静态构建，改完源码必须 `pnpm build` 重建 dist，否则线上看的还是旧页面。

## 七、顺带修掉的一个既有测试缺陷

`test_screener_run_all_progressive.py` 存在**约 40% 概率的竞态失败**（基线复现，
与本次功能无关）：

- 缓存是**逐策略增量写**的，而 `record_run_timings` 在循环**结束后**才执行；
- 测试等缓存齐了就断言 timings → 时序上不成立。

修法：新增 `_wait_run_timings()` 单独等耗时落盘，不复用「缓存就绪」的等待。
修复后连跑 6 次全过。

## 八、仍然没做的

- **行动卡只覆盖技术面**。财报/公告只给「去哪查」，不做自动解析与结论。
- **强弱判定是规则投票，不是统计模型**。没有回测过这套投票的历史有效性。
- **计划与实际成交不自动对账**。用户在模拟盘成交后需手动把批次标记 `done`
  或删除计划（未来可接 `paper.load_fills` 自动匹配）。
- **未做组合级的计划合计**。多只票的分批计划加起来会不会超过可用资金，目前不校验。
- 前端未接入三态分类总览页（API 已就绪，`positionClassify` 可用）。
