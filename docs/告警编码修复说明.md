# 告警文件编码损坏的根因与修复

> 事故时间：2026-11-05 ~ 11-07（计划任务每日运行）
> 影响：`data\user_data\alerts.jsonl` **29 行损坏**（占 12%），中文全部乱码且 JSON 语法无效
> 修复：`alert_io.py`（新）+ `policy-radar.ps1` / `policy-calendar.ps1` / `event-ledger.ps1`
> 隔离：`quarantine_alerts.py`

---

## 一、现象

告警文件里出现这样的行：

```json
{"ts": 1793787976704, "source": "policy_radar", "type": "policy_鏀跨瓥",
 "name": "鍒涗笟鏉?0ETF鏅『",
 "message": "鈻?鍒╃┖路鏀跨瓥 | 娆у厓鍖洪€氳儉鍗囪嚦鐩爣涓ゅ€嶏紝12鏈堝姞鎭笌鏈熷崌娓?| ... }
```

特征：
1. 中文变乱码（`鏀跨瓥` = `政策` 被错误解码）；
2. 行内出现 `?`（0x3F）；
3. **JSON 语法也坏了** —— `json.loads` 抛 `Expecting ',' delimiter`。

第 3 点最致命：`alert_store.list_recent()` 对坏行是

```python
try:
    ev = json.loads(line)
except Exception:
    continue          # ← 静默跳过
```

所以前端看到的告警**凭空少了一批**，日志里一个字都没有。

## 二、根因

### 2.1 链路

```
python (UTF-8 写 stdout)
   → PowerShell `& $py $script` 捕获（按 [Console]::OutputEncoding 解码）
      → 追加写入 alerts.jsonl
```

### 2.2 触发条件

交互式终端里 `[Console]::OutputEncoding` 是 **utf-8**，这条路看起来没问题 ——
所以手动运行一直正常，问题只在**计划任务**里出现。

`Task Scheduler` 启动的进程**没有交互式控制台**，代码页是 **GBK(936)**。
此时 PowerShell 会拿 GBK 去解码 python 输出的 UTF-8 字节。

### 2.3 为什么 JSON 结构也会坏

这不是"中文变乱码"那么简单。实测复现（在 GBK 控制台下捕获同一段 JSON）：

```
预期: {"ts": 1, "message": "▲ 利好·政策 | 创业板50ETF景顺"}
实际: {"ts": 1, "message": "鈻?鍒╁ソ路鏀跨瓥 | 鍒涗笟鏉?0ETF鏅『"}
```

`▲`(E2 96 B2) 被 GBK 读成 `E2 96`='鈻' + 剩余 `B2` 去吞下一个字节 → 下一个字节
本来是**空格**，被吞掉后变成 `?`。同理 `鏉?0ETF` 里的 `?` 吃掉了原本的字符。

当被吞掉的字节正好是 JSON 的 **`"`（0x22）** 时，闭合引号消失，
整行 JSON 从语法上就无效了 —— 这就是 `Expecting ',' delimiter` 的来源。

### 2.4 为什么不可逆

`?` 是解码失败时的**替换符**，原始字节已经不可知。实测：

```
29 行损坏 → 「GBK 回编 → UTF-8 解码」严格还原: 0 行成功
           （全部因 PUA 字符/'?' 无法编回 GBK 而失败）
```

所以这些行**只能隔离，不能修复**。

## 三、修复

### 3.1 核心思路：数据不再经 stdout 传递

旧做法让数据穿过一个"按控制台代码页解码"的环节，而这个代码页**取决于谁启动进程**。
只要还走 stdout，就永远受制于 `[Console]::OutputEncoding`。

新做法：

```
python  ──写 UTF-8 原子文件──▶  _alerts_outbox.jsonl
                                        │
shell   ──按字节读取、逐行验 JSON、追加──▶  alerts.jsonl
```

编码只在各自进程内发生**一次**，与任何代码页无关。

### 3.2 落盘前的最后一道闸

`alerts.jsonl` 的读取方对坏行是静默跳过 —— 坏数据一旦写进去就**很难发现**。
所以 shell 搬 outbox 前逐行 `ConvertFrom-Json` 校验：

- 合法行照常写入；
- 坏行**丢弃并记日志**，不灌进数据湖；
- 上游 python 侧另有 `alert_io.validate_jsonl()` 可做同样校验。

### 3.3 兜底：即使还有别的坑，也不再取决于代码页

三个 ps1 脚本开头都显式：

```powershell
[Console]::OutputEncoding = New-Object System.Text.UTF8Encoding($false)
```

子进程输出（仅用于日志，不承载数据）改用
`ProcessStartInfo.StandardOutputEncoding = UTF8` —— 显式指定解码方式，
不受父进程代码页影响。

### 3.4 改动清单

| 文件 | 改动 |
|---|---|
| `alert_io.py` | **新增**：UTF-8 原子写 outbox + JSONL 校验 |
| `policy_radar.py` | `emit_alerts` / `emit_news` 改为写文件，不再 print 标记块 |
| `policy_calendar.py` | 同上（告警 + 日历 JSON） |
| `policy-radar.ps1` | 按字节搬运 outbox + 逐行验 JSON + 钉编码 |
| `policy-calendar.ps1` | 同上 |
| `event-ledger.ps1` | 子进程输出显式按 UTF-8 解码（该脚本不传数据，只改日志解码） |
| `quarantine_alerts.py` | **新增**：隔离不可逆损坏行（备份 + 原子重写） |

> 兼容性：`alert_io.py` 与两个 ps1 是同一套改动，**不能只升级其中一个**。
> 旧 python 配新 ps1 会因为找不到 outbox 而"无新增告警"（不会写坏数据），
> 新 python 配旧 ps1 同理。两者都会在日志里显示出来，便于发现。

## 七、同一批包装脚本的第二个坑：管道死锁（2026-11-08 实测）

编码问题修好之后，同一批 `.ps1` 又暴露出**另一个独立的 bug**，症状完全不同：
任务"启动"了但永远跑不完。

**现象**：真实运行卡死 17 分钟；脚本日志只有"政策雷达启动"一行（41 字节）；
python 进程 CPU 冻结在 2.5s、`Get-NetTCPConnection` 显示没有任何网络连接；
`alerts.jsonl` 与 outbox 都没有变化。

**根因**：这三个脚本原来是

```powershell
$stdout = $proc.StandardOutput.ReadToEnd()   # 先读 stdout 到 EOF
$stderr = $proc.StandardError.ReadToEnd()    # 再读 stderr
$proc.WaitForExit()
```

而 python 的 **tqdm 进度条是写 stderr 的**。stderr 管道（约 4KB）一写满，子进程
就阻塞在"写 stderr"上，永远不会关掉 stdout；父进程正卡在"读到 stdout 结束"，
于是双方互等 —— 典型的双向管道死锁。CPU 0%、无网络连接、无落盘，全都对得上。

**修法**：两个流并行异步读（`ReadToEndAsync()` 会立刻开始抽干各自的管道）。

```powershell
$outTask = $proc.StandardOutput.ReadToEndAsync()
$errTask = $proc.StandardError.ReadToEndAsync()
$proc.WaitForExit()
$stdout = $outTask.Result
$stderr = $errTask.Result
```

**对照实验**（`D:\deepseek_path\.tspcheck\pipe_deadlock_test.ps1`：子进程先往
stderr 写 N KB，再往 stdout 写结束标记；**校验实收字节数**，避免"没死锁"其实
是子进程根本没跑起来）：

| stderr 输出量 | 旧写法 | 新写法 |
|---|---|---|
| 300 KB | >30s 挂住，实收 0 KB | 0.4s，实收 303 KB |
| 5000 KB | >30s 挂住，实收 0 KB | 0.9s，实收 5049 KB |

> 教训：第一版对照实验里"旧写法 0.4s 通过"是**假阴性** —— 函数参数没传进
> `Start-Job` 的作用域，子进程压根没启动。测"会不会挂"必须同时校验**收到的
> 字节数**，否则测的是空气。

**修复后的真机验证**：`policy-radar.ps1` 完整跑完，693s、exit 0、新增 10 条告警；
随后用 `Start-ScheduledTask` 在真实计划任务环境再跑一次确认。
