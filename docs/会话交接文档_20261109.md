## 二、本会话完成的七项工作

### 工作流 1：告警文件编码损坏（29 行不可逆）—— 已修复

**现象**：`alerts.jsonl` 曾损坏 29 行（12%），中文乱码且 JSON 语法无效。
`alert_store` 对坏行是 `except: continue` → **告警静默消失**，无任何日志。

**根因（已复现）**：计划任务由 Task Scheduler 启动、无交互控制台，代码页是
**GBK(936)**；旧链路 python 把 UTF-8 JSONL 打到 stdout、PowerShell 用
`& $py $script` 捕获。GBK 的双字节序列会**吞掉 JSON 的结构字符 `"`(0x22)**，
非法字节又被替换成 `?` → 整行语法即坏。交互式终端是 utf-8，所以手动跑一直正常。

**不可逆性**：29/29 行无法通过「GBK 回编 → UTF-8 解码」还原（`?` 是替换符，
原字节已不可知）。只能隔离。

**修法**：数据不再经 stdout —— python 写 UTF-8 原子 outbox 文件，shell 按字节搬运
（`alert_io.py`）。落盘前逐行验 JSON，坏行丢弃不写入。

**结果**：249 行 → 219 行（隔离 29 行），之后新写入全部正常。
产物：`alerts.corrupt-20261108-080859.jsonl`（事故证据，原样存档）、`alerts.bak-*.jsonl`。

### 工作流 2：包装脚本管道死锁 —— 已修复（真实卡死 17 分钟）

**现象**：真实运行卡死 17 分钟，日志只有"启动"一行，python CPU 冻结在 2.5s、
无任何网络连接。

**根因**：旧写法是 `ReadToEnd(stdout)` → `ReadToEnd(stderr)`，而 python 的 tqdm
进度条写 **stderr**；stderr 管道（约 4KB）写满后子进程阻塞，永不关闭 stdout，
父进程死等 → 双向死锁。

**修法**：两个流并行异步读（`ReadToEndAsync` + `WaitForExit` + `.Result`）。
三个脚本（`policy-radar.ps1` / `policy-calendar.ps1` / `event-ledger.ps1`）都改。

**对照实验（必须校验收到的字节数）**：

| stderr 输出量 | 旧写法 | 新写法 |
|---|---|---|
| 300 KB | >30s 挂住，实收 0 KB | 0.4s，实收 303 KB |
| 5000 KB | >30s 挂住，实收 0 KB | 0.9s，实收 5049 KB |

> **教训**：第一版实验报"旧写法 0.4s 通过"是**假阴性** —— 参数没传进
> `Start-Job` 作用域，子进程压根没启动。测"会不会挂"必须同时收多少字节。

### 工作流 3：告警字段补齐（用户要求的 5 项）—— 已落地

每条政策/新闻告警都带：

| 要求 | 字段 |
|---|---|
| ① 来源/链接/时间 | `source_name` `source_url` `source_host` `published_at` `event_date` `effective_date` `fetched_at` |
| ② 来源等级+理由 | `source_tier` `source_tier_label` `source_tier_reason` `source_verifiable` |
| ③ 映射证据 | `mapping_evidence`（个股=行业/概念命中；ETF=当日成分股与权重）`ai_evidence` |
| ④ 影响路径+不确定性 | `impact_path` `impact_path_text` `directness` `uncertainty` |
| ⑤ 核实状态 | `verification` `verification_label` `verification_note` |

**来源分级**（`source_grade.py`）：`official` 官方原文 / `company` 公司公告 /
`official_media` 官方媒体 / `media` 媒体转述 / `unverified` 待核实。
**不给 0~1 分值** —— 分数无法复核，域名可以。

**关键修复**：`_norm()` 原来把采集接口的「链接」列丢了 → 新闻告警天生没有 url。

**核实状态取两维度中最弱一环**：官方文件 + 语义推测的映射，结论仍是「系统推断」。

### 工作流 4：同一事件归组（用户第 1 组要求）—— 已落地

三个 ID 各管一件事：

| 字段 | 含义 | 生成 |
|---|---|---|
| `event_id` | **单条**报道 | `sha256(标题\|主体\|事件日)` |
| `event_group_id` | **同一件事** | 落盘注册表分配，一旦分配永久复用 |
| `event_update_seq` | 第几次进展 | 注册表递增 |

**判组三条路径**（同一事件日 + 主体相容是前提）：
1. 指纹全等；
2. 相似度 ≥ **0.72**（与离线链路同口径）；
3. 转述改写：`0.40 ≤ 相似度 < 0.72` **且** 去填充词后实词 bigram 重合 ≥ 2。

**阈值取证**（43 条真实标题、903 组配对）：

| 类别 | 实测相似度 |
|---|---|
| 同一件事（≥0.72） | 0.87 / 0.77 / 0.73 / 0.72 |
| 同一件事（转述改写） | 0.59 / 0.57 / 0.55 / 0.42 / 0.41 |
| **不同**事件（同"数据中心"家族） | 最高 **0.21** |

0.40 落在 0.21~0.41 的空带里。**光看实词重合没用**——不同事件也常共享 3~6 个实词。

**两条铁律**：
- 相似度合并不跨事件日（否则 3 月与 6 月的"央行降准"会被并成一件事）；
- 更新基准用 `last_update_at` 而非最新报道时间，间隔 ≥ 6h 才算新进展
  （否则并排转载会把基准顶高，真后续永远追不上）。

**去重键**改为 `(事件组, 个股, 方向, 更新序号)` —— 同组同序号不重报，真后续仍报一次。

### 工作流 5：ETF 成分股快照 + 事件暴露（用户第 2 组要求）—— 已落地

**为什么必须按天落盘**：`akshare.fund_etf_holdings_tx` **没有报告期列**，
权重是「最新价×数量」的行情估值 —— 今天取和明天取就不一样。写"40% 权重受影响"
却不说哪天的口径，既无法复核也无法回溯。

三个时点分开写，不知道的写 `null`：

| 字段 | 含义 | 实测 |
|---|---|---|
| `observed_at` | 抓取日 | 2026-11-09 |
| `weights_as_of` | 权重反映时点 | 2026-11-09 |
| `report_period` | 基金报告期 —— **接口没有** | `null` |
| `weight_basis` | 权重怎么算的 | 市值占比（最新价×证券数量，行情估值） |

**实测印证"按名字猜主题是错的"**：

| ETF | 名字 | 前三大真实持仓 |
|---|---|---|
| 159529 | 标普**消费**ETF景顺 | `AMZN 13.53% / TSLA 12.82% / WMT 7.83%` |
| 159682 | 创业板50ETF景顺 | 宁德时代 18.89% / 中际旭创 12.48% / 东方财富 7.33% |
| 159586 | 计算机ETF南方 | 科大讯飞 5.47% / 金山办公 4.74% / 同花顺 4.14% |

**事件暴露字段**：`affected_weight_pct` `affected_constituents` `by_direction`
`bullish_weight_pct` `bearish_weight_pct` `unknown_direction_weight_pct`
`direction_conflict` `conflict_note`。

实测（159682）：受影响 31.38%，其中利好 12.48% / 利空 18.89% → `direction_conflict=true`。

**三条不许越界**：成分缺失 → `precise=false` +「无法精确评估」（不给数字）；
权重为 0 不算暴露；「没受影响」≠「没风险」。

### 工作流 6：实际持仓 vs 自选观察（用户第 2 组后半）—— 已落地

三种 `basis`，调用方读它即可分辨：

| basis | 标签 | 权重含义 | 有成本/期限 |
|---|---|---|---|
| `actual_positions` | 实际持仓分析 | 市值 / **账户权益** | 有 |
| `watchlist_observation` | 自选股观察（不是组合） | 等权假设 | 无 |
| `caller_supplied_weights` | 调用方提供的权重（未核对账户） | 调用方给的数字 | 无 |

**关键口径**：权重分母是**账户权益（现金+市值）**，不是持仓市值之和 ——
否则 90 万现金 + 2 万持仓会被算成"满仓 2 只"（实测 2.17%，不是 100%）。

### 工作流 7：前瞻跟踪评测（用户第 3 组要求）—— 已落地

- **冻结**：记 `as_of` / `data_cutoff` / `generated_at` / `model_version` / `inputs_fingerprint`，
  存成只增不改的版本目录 `data/forecast_track/<kind>/<key>/vN.json`。
- **防泄漏**：`data_cutoff > as_of` 直接拒绝；评测只读 cutoff **之后**的行情；
  样本不足**不打分**（计入 `unscored`）。
- **扣费**：买 5bp + 卖 5bp + 印花税 5bp = 15bp；同时给回撤与换手（一次开平 = 2.0）。
- **三个概念分开**：方向准确率（分母只含给了明确方向且已打分的）/ 映射胜率 / 证据分层。
- **证据分层**：`verification >= reported` 且 `mapping_level ∈ {A,B}` → 「官方证据足/映射明确」，
  其余 → 「推测性主题关联」。
- **市场状态**自动取 regime 已算好的口径（`data/regime_history`，列 `state`），不另算一套。
