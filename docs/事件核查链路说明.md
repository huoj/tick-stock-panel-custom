# 事件核查链路（6 步可复核流程）

> 脚本：`D:\deepseek_path\databridge\event_review.py`
> 输出：`databridge\data\event_review\event_review-<时间戳>.json` + `latest.json`
> 输入：`tick-stock-panel\data\user_data\alerts.jsonl`（`source = policy_radar / policy_calendar`）
> 完成时间：2026-11-08

---

## 一、它补的是什么缺口

`policy_radar.py` 解决**发现**：把新闻变成告警推到通道里。
但它产出的是"一句话结论"（`message`），无法回答：

- 这条消息**原文在哪**？什么时候发的？我们什么时候抓到的？
- 政策的**生效日**是哪天（不是发稿日）？
- 这条是政府文件还是自媒体转述？
- 同一件事被五家媒体转载，算一次还是五次？
- 这个影响**落到哪只股票/哪只 ETF 的多少权重**上？
- 方向凭什么判利好，什么情况下会错？

本模块把每条告警还原成**可审计的事件对象**，回答上面每一问。

---

## 二、六步与各自防的错

| 步 | 做什么 | 防的具体错误 |
|---|---|---|
| 1 | 原始归档：ID/标题/正文/来源/链接/发布时间/抓取时间/类型/证券 | `alerts.jsonl` 只留 7 天，过期即删，且原文链接/发布时间很多本就没进告警 → **不存档就无法复核** |
| 2 | 标准化事件，**三日期分离** | 把"三个月后生效"当"今天已生效" → **前视偏差** |
| 3 | 来源分级 + 理由 + 原文链接 + 独立源确认 | 只给 0~1 的"可信度分数"→ **无法复核、无法反驳** |
| 4 | 精确匹配 + 相似度聚类成事件簇 | 同一条消息五家转载 → **重复计五遍利好** |
| 5 | 个股按行业/概念/业务词；ETF 按**当日成分股权重** | 把"主题"当持仓 → 实测 159529 标普消费ETF 实际持仓是 AMZN/TSLA/WMT |
| 6 | 方向/渠道/短中长期/直接间接/强度/不确定性 | 按行业标签一律判利好 → **方向必须按公司自己的业务判断** |

## 三、关键设计决策（都有实测依据）

### 3.1 三日期必须分开，缺失就是 `unknown`

```
event_date      事件发生/公布日
effective_date  政策生效日（可能是未来）
fetched_at      我们抓到它的时间（=「当时已知」的上界）
```

解析只接受**能无歧义落地**的写法（`2026-12-01`、`2026年12月1日`、`12月1日`）。
`近期` / `择机` / `适时` / `尽快` 一律 `unknown` —— 它们不是日期，让模型去"合理推断"
就是在制造前视偏差。

> 实测：全量 42 条事件里 `effective_date` 全部 `unknown`。这不是 bug，是因为
> 现有告警文本本来就没写生效日。**标 unknown 比编一个日期有用得多。**

### 3.2 `published_at` 的口径要标出来

实测发现 `policy_radar.build_alert()` **从没把 `event_src_time` 落进告警**，
所以历史告警里没有原文发布时间。此时退回告警自身的 `ts`（= 第一次看到它的时间），
但必须在 `published_at_kind` 里写明是 `source` 还是 `alert_ts`，
否则下游会把它当成准确的发布时间。

> 这是"两个都叫时间但含义不同"的典型陷阱。字段名一样，语义必须分开。

### 3.3 来源等级不给分数

离线核查与在线告警**共用同一张等级表**（`databridge/source_grade.py` 的
`TIERS`，离线链路的 `SOURCE_TIERS` 直接引用它）。同一条消息不该在两份报告里
有两种说法 —— 早先离线链路自己维护过 `primary/secondary/unverified` 一套，
与在线的五级并存，已统一：

| 等级 | 含义 | 判定依据 |
|---|---|---|
| `official` 官方原文 | 发布主体 = 事件主体 | gov.cn / csrc.gov.cn / pbc.gov.cn / sse.com.cn / szse.cn … |
| `company` 公司公告 | 上市公司自己的公告 | cninfo 等公告通道 |
| `official_media` 官方媒体 | 官方喉舌 | 新闻联播 / 新华社 / 人民网 / 央视 |
| `media` 媒体转述 | 财经媒体转述，原文可追溯 | 同花顺 / 东方财富 / 财联社 / 新浪财经 / 富途 |
| `unverified` 待核实 | 无来源、无法追溯 | 其余 |

两条容易踩的规则：

1. **链接指向更高等级来源时可以抬高等级**：媒体转述一篇政府原文、链接直接
   指向 `gov.cn`，就按 `official` 算。
2. **在线链路判过的等级直接沿用，不重新推断**。采集通道名（同花顺/财联社/
   新闻联播）只有在采集当场才知道，告警落盘时并未保留通道，事后只凭域名会把
   "财联社（该接口不提供链接）"从 `media` 误判成待核实 —— 同一来源出现在
   在线告警和核查报告里就成了两种说法。因此第 1 步归档必须把 `source_url`
   与 `source_tier*` 一起搬到下游（这是实测踩过的坑：字段在第 1 步就丢了，
   后面两步判得再对也没用，12 条带链接的新告警仍显示"待核实 12/12"）。

原文链接字段有三种历史写法 `url` / `source_url` / `link`，三条都要认。

理由写成可核对的句子：`域名 www.csrc.gov.cn 属于官方原文，已提升等级`。
**独立源确认按不同域名数计**（同一家发三篇 ≠ 三个来源）。

### 3.4 聚类只在同一事件日内做

同一句话在不同日期是两件事。典型反例：

```
3月  央行降准   ← 一次
6月  央行降准   ← 另一次
```

若相似度跨日期合并，会**直接吞掉一次事件**，而且历史台账里极难发现。
所以相似度合并前先比较 `event_date`，不同就不合并。

簇标 `counted_once: true`，上层按簇汇总，不按报道条数累加。

### 3.5 ETF 必须按真实成分股，不能按名字

`fund_etf_holdings_tx`（腾讯）实测可用，返回当日成分股与 `市值占比`。

```
159682 创业板50ETF → 宁德时代 18.89%、中际旭创 12.48%、东方财富 7.33%
159529 标普消费ETF → AMZN 13.53%、TSLA 12.82%、WMT 7.83%   ← 名字叫"消费"，持仓是美股
```

三种结论必须分开，混在一起会让人误判覆盖度：

| 情况 | 含义 |
|---|---|
| `precise=true, matched=true` | 有成分股权重支撑且真命中 |
| `precise=true, matched=false` | 核对过全部成分股 → **结论是"无影响"**（这也是结论） |
| `precise=false` | 缺成分股数据 / 命中权重 < 0.5% → **无法给结论** |

> 权重阈值 0.5%：低于它的单只成分股对净值几乎没有拉动，拿它说"这个事件影响该 ETF"
> 是过度解读。实测曾有 1 只成分股命中但权重 0.00% 却被判为"精确映射"，已修正。

### 3.6 方向必须按公司业务判断

同一个"数据中心建设"事件，AI 对三只票给出的结论完全不同（实测输出）：

| 证券 | 方向 | 渠道 | 理由 |
|---|---|---|---|
| 美的集团 | 不确定 | revenue | 数据中心温控需求间接传导，但**需经海外渠道，收入弹性有限** |
| 格力电器 | 不确定 | revenue | 主营空调，**数据中心制冷关联弱** |
| 中国移动 | 不确定 | valuation | 海外算力资本开支与公司**国内业务无直接关联**（directness=无） |

这正是要的效果：**不因为"属于某行业"就一律判利好**。
方向大面积是"不确定"不是失败，而是模型在证据不足时保持诚实。

### 3.7 AI 失败必须降级且标注

`degraded=true` 表示该条走了确定性规则。规则**只给能确定的部分**（相关性、直接/间接），
方向一律 `不确定` —— 规则没法判断"加息对这家公司是利好还是利空"，
猜错比标 unknown 更有害。

## 五、已知限制（必读）

| 限制 | 说明 |
|---|---|
|---|---|
| **历史告警没有原文链接** | 修复后的采集已保留链接，但**修复前落盘的告警无法补**：全量 59 条 policy 告警里只有 10 条带 `source_url`（= 最近一次真实运行产出的），其余只能判"待核实" |
| **现有告警没有原文发布时间** | 历史记录 `published_at_kind=alert_ts`，是下界不是准确发布时间；新告警已有 `published_at` |
| **生效日普遍 unknown** | 新闻源本身不写生效日。要精确得接入政府公报原文 |
| **方向判断仍是推断** | AI 给的是"可能性排序"，已用"必须说出渠道+假设+不确定处"约束，但不能根除 |
| **无历史事件库** | 免费新闻源历史只有几小时 → 无法回测"这个方法赚不赚钱" |

> 定位与 `policy_radar.py` 一致：**是核查与排雷工具，不是交易信号。**

## 六、测试

```powershell
cd D:\deepseek_path\databridge
.\.venv\Scripts\python.exe -m pytest tests/ -q
```

41 项，覆盖的都是**会产生错误结论**的点，不是"函数能被调用"：

- 三日期分离、`unknown` 不被猜、相对时间词不落成日期
- 精确匹配/相似度聚类、**跨日期不合并**、每篇报道保留为证据
- 来源等级判定、不返回神秘分数、独立源按域名计
- 在线/离线**共用同一张等级表**、在线判过的等级被沿用而非重推、
  归档不丢 `source_url`（字段漏搬过一次，见 3.3）
- ETF 按真实权重、无数据标"无法精确映射"、**主题词不当持仓**、低权重剔除
- AI 输出非法枚举被收敛、规则降级不猜方向

## 七、配套的告警编码修复

本模块依赖 `alerts.jsonl`，而该文件此前曾损坏 29 行（中文乱码、JSON 语法错误）。
根因与修法见 [`告警编码修复说明.md`](./告警编码修复说明.md) 与 `alert_io.py` 的模块注释。

简要结论：计划任务的 GBK 控制台解码 python 的 UTF-8 输出，**吞掉了 JSON 的引号**。
现在数据只经文件传递（python 写 UTF-8 / shell 按字节搬运），编码只在各自进程内发生一次。

## 八、配套的告警字段契约

本文档描述的是**离线核查**链路（读 `alerts.jsonl` → 输出 `event_review-*.json`）。
与之并行，在线采集链路（`policy_radar.py` → `alerts.jsonl`）也已按同一套口径补齐字段：
原文链接、来源等级与理由、映射证据（个股标签或 ETF 当日成分股与权重）、
影响路径与不确定性、以及「待核实」状态。

字段清单、定级规则与实测样张见 [`告警字段契约.md`](./告警字段契约.md)。
两条链路的日期口径、来源分级（`source_grade.py`）与 ETF 成分股口径
（`event_review.load_etf_constituents`）是**共用**的，避免同一事实出现两种说法。

### 8.1 在线链路的事件归组（2026-11-09）

在线链路新增了**事件级归组**：`event_group.py` 把同一政策的转载、摘要与
后续报道归到一个稳定 `event_group_id`（组 ID 靠 `data/event_groups.json`
注册表保持稳定），新进展记 `event_update_seq`，并据此去重
（键 = 事件组 × 个股 × 方向 × 更新序号）。

离线链路本就有等价机制（`build_clusters`，阈值同为 0.72），两者关系是：
**在线归组决定"要不要再报一条告警"，离线聚类决定"这一批证据算几件事"**。
两条链路都遵守同一条铁律：相似度合并不跨事件日（否则 3 月与 6 月的
"央行降准"会被并成一件事）。

字段、判组规则、注册表与接口契约见
[`告警字段契约.md`](./告警字段契约.md) 第八、九节。
