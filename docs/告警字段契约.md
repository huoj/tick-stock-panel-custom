# 政策 / 新闻告警的字段契约（每条必须能回答 5 个问题）

> 完成时间：2026-11-08
> 改动文件：`databridge/policy_radar.py`、`databridge/policy_calendar.py`、
> `databridge/source_grade.py`（新）、`databridge/symbol_util.py`（新）
> 对应问题：**"这条告警是事实还是系统猜的？依据是什么？"**

---

## 一、起因

用户对告警接口的反馈（原文要点）：

> 部分告警来源是新闻标题或汇总内容，映射理由含 AI 判断与模糊匹配；
> 例如 ETF 被关联到「新能源」「半导体」主题后就推断成分股受影响 ——
> **这只能作为线索，不能当成已核实的个股影响结论。**

要求每条政策/新闻事件都保留 5 项：

1. 原始来源、原文链接、发布时间、事件发生/生效日期
2. 信息来源等级及其理由（官方原文 / 公司公告 / 媒体转述 明确区分）
3. 映射证据：公司业务、具体受影响产品/地区，或 **ETF 对应日期的实际成分股和权重**
4. 影响路径与判断不确定性（如「关税→出口成本→利润」），标明直接/间接
5. **「待核实」状态**，供用户区分事实与系统推断

## 二、字段对照表

每一条 policy/news 告警都带以下字段（`alerts.jsonl` 每行一个 JSON）。

### 1️⃣ 来源与时间

| 字段 | 含义 | 缺数据时 |
|---|---|---|
| `source_name` | 采集通道名（同花顺/东方财富/财联社/富途/新闻联播/公司公告） | 必填 |
| `source_url` | **原文链接** | `null` |
| `source_host` | 链接域名 | `null` |
| `published_at` | 原文发布时间 | `null` |
| `event_date` | 事件**发生**日 | `"unknown"` |
| `effective_date` | 事件**生效**日（政策常写"自 2027 年起"） | `"unknown"` |
| `fetched_at` | 采集时刻 | 必填 |

> 采集接口本来就有链接：`stock_info_global_ths` / `_em` / `_futu` 都有「链接」列，
> 但旧代码 `_norm()` 只保留 `title/content/time`，把链接丢了 ——
> 所以新闻类告警**天生没有 url**。现在保留，并截断到 300 字符。
> 财联社接口（`stock_info_global_cls`）确实不提供链接，故其告警 `source_url=null`。

**三日期严格分离**，不许互相顶替：发布日 ≠ 事件发生日 ≠ 生效日。
原文没写就写 `unknown`，**不许用今天日期凑数，也不许从"近期/择机/适时"推断**。

### 2️⃣ 来源等级与理由

| 字段 | 含义 |
|---|---|
| `source_tier` | `official` / `company` / `official_media` / `media` / `unverified` |
| `source_tier_label` | 中文标签：官方原文 / 公司公告 / 官方媒体 / 媒体转述 / 待核实 |
| `source_tier_reason` | **人类可读的理由**，不是分数 |
| `source_verifiable` | 有原文链接可点开核对吗 |

判定顺序：**采集通道优先**（比域名可靠），域名可以**抬高**等级
（媒体接口转载政府原文，链接指向 `gov.cn` → 升为 `official`）。
公司公告即使没有链接仍是 `company`（主体是公司自己），但会标注"缺原文链接"。

> 刻意**不返回 0~1 的数值分数**：分数无法核对也无法反驳，
> 只会给人"很科学"的错觉。

### 3️⃣ 映射证据

个股（`mapping_evidence.kind = "stock_tags"`）：

| 字段 | 含义 |
|---|---|
| `industry` | 该股行业标签（东方财富/同花顺） |
| `matched_on` | 命中的具体标签，如 `["数据中心"]` |
| `how` | 命中方式：`exact_industry` / `exact_concept` / `synonym_*` / `partial` |
| `ai_evidence` | AI 给出的具体业务/产品/地区 |

ETF（`mapping_evidence.kind = "etf_constituents"`）：

| 字段 | 含义 |
|---|---|
| `as_of` | 成分股数据日期 |
| `source` | 数据源（`akshare.fund_etf_holdings_tx`） |
| `precise` | 是否拿到了当日成分股（拿不到 → 结论只能是"无法精确映射"） |
| `matched_weight_pct` | **字面命中**成分股的合计权重（%） |
| `matched` | 命中明细：`code / name / weight_pct / matched_on / how / exact` |
| `synonym_weight_pct` | 仅同义词命中的合计权重（**不计入定级**） |
| `synonym_matched` | 同义命中的成分股名（线索，仅供参考） |

**ETF 绝不再按基金名字猜主题**：旧代码有一张 `ETF_THEME_KW` 表，
按名字里的"消费""计算机"推断持仓，实测给出完全错误的结论 ——
`159529 标普消费ETF` 的真实持仓是 **AMZN 13.53% / TSLA 12.82% / WMT 7.83%**（美股），
按名字会被映射到 A 股消费板块。该表已删除，并有回归测试
（`assert not hasattr(pr, "etf_theme")`）。

### 4️⃣ 影响路径与不确定性

| 字段 | 含义 |
|---|---|
| `impact_path` | 分步传导链，如 `["美国撤销部分对华关税","空调出口成本下降","海外毛利率改善"]` |
| `impact_path_text` | 上者的可读串 |
| `directness` | `直接` / `间接` / `无` / `unknown` |
| `uncertainty` | 这条判断**最不确定的地方**（AI 必须回答） |
| `ai_evidence` | 落到这只股票哪块业务上 |

prompt 里明确规定：路径写 2~3 步、必须能落到"这只股票的钱"（收入/成本/订单/产能）、
**写不出中间环节就应该判 `link="无"`**，不许写"提升竞争力"这类空话。

### 5️⃣ 核实状态

| 字段 | 含义 |
|---|---|
| `verification` | `fact` / `reported` / `inferred` / `pending` |
| `verification_label` | 已核实事实 / 媒体报道 / 系统推断 / 待核实 |
| `verification_note` | 两个维度的理由拼起来的说明 |
| `event_verification` | 事件维度：一手文件 / 报道 / 缺链接 |
| `mapping_verification` | 映射维度：`evidenced` / `inferred` / `pending` |

**总状态取两个维度中"最弱"的一环**：

```
事件维度：fact(一手文件) / reported(媒体报道) / pending(缺链接)
映射维度：evidenced(A/B级有依据) / inferred(推测) / pending(缺成分股)
总状态 = 较弱的那一个
```

一条官方文件配上语义推测的映射，结论仍然是「系统推断」——
**不能因为来源权威就把映射也说成事实。**
反过来，官方文件 + A/B 级依据 → 「已核实事实」；媒体转述 + A/B 级依据 → 「媒体报道」。

## 四、已知限制（如实标注）

| 限制 | 说明 |
|---|---|
| `effective_date` 常年 `unknown` | 现有告警原文基本不写生效日，链路**刻意不猜**；这是数据源的缺口，不是解析失败 |
| 同义词命中只能到 C | 同义词表为"不漏报"而放宽，含包含/跨类关系；宁可标成线索 |
| ETF "字面命中"仍可能偏宽 | 同花顺概念标签本身较宽（如 18/50 只创业板50成分股带"数据中心(AIDC)"概念）。明细列出全部名称与权重，可自行核对 |
| ETF 命中集合跨轮次会变 | 5 轮一致性测试：4 只标的中 3 只完全一致，`159586` 的命中事件在轮次间不同。**"这次影响了哪只股票"不是确定性结论** |
| `link` 仍是 AI 判断 | 只有"说无就降 D"这一条硬约束 |
| D 级仍会输出 | 只标"推测"，不滤掉；可以无视 D 级 |

## 五、怎么自己核对一条告警

> **第一步**：点开 `source_url`，看原文有没有这回事（没有链接 → 状态就是「待核实」）。
> **第二步**：看 `mapping_evidence`——
> 个股是"哪个行业/概念标签命中"，ETF 是"当日哪些成分股、各多少权重"。
> **第三步**：看 `impact_path` 能不能落到**收入 / 成本 / 订单 / 产能**上。
> 落到"偏好 / 情绪 / 预期"的，基本是噪音。

## 八、同一事件归组（2026-11-09 新增）

### 8.1 为什么要做

`alerts.jsonl` 实测 242 条里，`source=paper` 的模拟成交日志占 **177** 条，
policy 类只有 64 条 —— 默认列表把成交日志与政策新闻混在一张表里，
用户很容易把"模拟买入 100 股"和"国常会稳市机制"当成同一类信息读。
另一半问题是政策新闻**同一件事被多家媒体转载**：按告警条数累加，
一次政策会被读成好几份利好。

### 8.2 三个 ID 各管一件事（不能混用）

| 字段 | 含义 | 生成方式 | 解决什么 |
|---|---|---|---|
| `event_id` | **单条**报道的身份 | `"evt_"+sha256(标题\|主体\|事件日)[:16]` | 同一条原文反复落盘时不重复 |
| `event_group_id` | **同一件事**的稳定 ID | 落盘注册表分配 `"evtgrp_"+sha256[:16]` | 多家转载合并计一次 |
| `event_update_seq` | 这件事的**第几次进展** | 注册表递增（首次为 1） | 真后续要再报一次 |

配套字段：`is_event_update`(bool)、`event_sources`(组内全部来源证据)、
`event_source_count`(家数)、`event_title`(事件级标题)。

> 注意 `event_id` **不能**用来归组：实测三家媒体报同一政策，
> 三条的 `event_id` 各不相同（措辞不同 → 哈希不同），这正是需要
> `event_group_id` 的原因。这一点有单测锁住。

### 8.3 两条判组规则（阈值来自实测，不是拍脑袋）

1. **精确**：指纹全等（含主体与事件日）。
2. **相似**：字符 bigram Jaccard ≥ **0.72** —— 与离线核查链路口径一致。
3. **转述改写**：`0.40 ≤ 相似度 < 0.72` 且**实词 bigram 重合 ≥ 2**
   （去掉"考虑/拟/将/扩大/布局/项目…"这类填充词后再比）。

取证（`probe_group_rule.py`，43 条真实标题、903 组配对）：

| 类别 | 实测相似度 | 结论 |
|---|---|---|
| 同一件事（≥0.72） | 0.87 / 0.77 / 0.73 / 0.72 | 4 对，逐对核对全是同一件事 |
| 同一件事（转述改写） | 0.59 / 0.57 / 0.55 / 0.42 / 0.41 | 5 对，逐对核对全是同一件事 |
| **不同**事件（同关键词"数据中心"） | 最高 **0.21** | 谷歌马来西亚 / 美内华达反对 / 字节巴西 / Anthropic 采购 |

0.40 恰好落在 0.21~0.41 的空带里。**光看实词重合没用**：不同事件
也常共享 3~6 个实词（都含"数据中心""投资""扩建"），所以实词重合
必须与相似度下限合用 —— 这条差点写错。

### 8.4 两条容易做错的地方（都有测试与真实数据兜底）

- **跨日期不能随便并**：指纹必须含 `event_date`，否则 3 月与 6 月的
  "央行宣布降准"会被并成一件事（离线链路踩过这个坑）。跨日期合并还要
  额外过一道"后续窗口"闸门：7 天内视作同一件事的后续，且窗口**锚在首次
  出现时间**而不是"上次更新"，否则每 6 天一条同题报道会把周期性事件
  永久并成一组（链式延长）。
- **更新基准不能取"最新一条报道时间"**：并排转载会把基准顶高，真正的
  后续永远追不上。基准用 `last_update_at`（上次判定为新进展的时间），
  间隔 ≥ 6 小时才算新进展；并排转载只追加来源、不增序号。

### 8.5 去重 key 跟着改

去重键从"个股+原文标题+方向"改成 **(事件组, 个股, 方向, 更新序号)**：
同一事件组、同一股票、同一方向**不再重复告警**；真出现新进展
（`event_update_seq` +1）仍会再报一次 —— 既去重又不漏后续。
历史告警没有组 ID 时回退旧 key。

### 8.6 注册表必须落盘（组 ID 稳定性的唯一来源）

`D:\deepseek_path\databridge\data\event_groups.json`（已加进 `.gitignore`，
属运行时状态）。**重新聚类会让同一事件换 ID、历史统计错位**，
所以组 ID 一旦分配就复用，新媒体加入组内只追加来源。

## 九、事件级接口契约（2026-11-09 新增）

| 接口 | 作用 | 关键参数 |
|---|---|---|
| `GET /api/alerts` | 原始告警列表（**未按事件归组**） | `days` `limit` `source` `type` `ext_columns` |
| `GET /api/alerts/summary` | **按来源/类型/事件分开计数** | `days` `limit` `source` `type` |
| `GET /api/alerts/event-groups` | 按事件归组的视图，**组内可展开全部来源证据** | `days` `limit` `group_limit` `source` `type` `kinds` `include_ungrouped` |

`summary` 的关键返回：

```jsonc
{
  "total": 249,
  "by_kind": { "trading": 177, "policy_news": 71, "other": 1 },   // 成交日志 vs 政策新闻分开
  "by_source": { "paper": 177, "policy_radar": 61, "policy_calendar": 3 },
  "events": {
    "count": 68, "alerts": 71, "ungrouped": 64,
    "multi_source": 0, "updates": 0,
    "by_direction": { "利好": 43, "不确定": 15, "利空": 10 },       // 按"事件数"计, 不是告警条数
    "by_verification": { "媒体报道": 6, "系统推断": 13, "待核实": 49 },
    "by_mapping_level": { "B": 13, "C": 16, "D": 2, "?": 37 }
  }
}
```

`event-groups` 每个事件含 `event_group_id / title / event_date /
effective_date / update_seq / has_update / alert_count / symbols / names /
directions / mapping_levels / verification`（**取组内最弱的一环**）/
`source_count / sources / first_ts / last_ts / alerts`（成员明细）。

两个设计细节：

- **路径不叫 `/events`**：`app/services/api_gateway.py:required_scope`
  把所有以 `/stream`、`/events`、`/analyze` 结尾的路径当 SSE 端点、
  直接不放行，普通 JSON 查询接口会被 Token 客户端拒之门外。
- **开放面是有意变更的**：两个新端点都是 `read:analysis` 只读聚合，
  已同步更新契约快照 `backend/tests/test_openapi_contract.py` 的
  `EXPECTED_OPEN_ENDPOINTS`（该测试要求"有意识地更新并在 commit 里说明"）。

### 9.1 如实说明的三条限制

1. **历史告警归不了组**：升级前落盘的 64 条 policy 告警没有
   `event_group_id`，接口只能让每条各自成组 —— 所以现在
   `events.count`（68）是**事件数的上界**，`ungrouped: 64` 明确标了出来。
   随着新告警落盘，这个数字会自然收敛。
2. **多家转载合并目前只有单测覆盖**：本次真实运行每个事件都只有 1 家来源
   （`event_source_count=1`、`multi_source=0`），去重合并逻辑尚未在真实
   数据上被触发过。
3. **接口只回答"有几件事"，不回答"这件事有多重要"**：方向按事件数计
   （三家转载 = 1 个利好），但方向本身是映射结论，可靠性看
   `mapping_levels` 与 `verification` 两个字段。

## 十、ETF 口径日与事件暴露（2026-11-09 新增）

### 为什么要"口径日"

`akshare.fund_etf_holdings_tx` 能给成分股与权重，但**没有报告期列**，权重是
「最新价 × 数量」的行情估值 —— 同一只 ETF 今天取和明天取就能不一样。
报告里写"这只 ETF 有 40% 权重受影响"必须能说清是哪天的口径，否则既无法复核
也无法回溯。所以改成**按天落盘快照**（`databridge/data/etf_holdings/<YYYY-MM-DD>.json`），
并把三个时点分开写，不知道的写 `null`：

| 字段 | 含义 | 实测取值 |
|---|---|---|
| `observed_at` | 我们抓取这份数据的日子 | `2026-11-09` |
| `weights_as_of` | 权重反映的时点（= 观测日，行情估值） | `2026-11-09` |
| `report_period` | 基金定期报告期 —— **接口没有 → null** | `null` |
| `weight_basis` | 权重怎么算出来的 | `市值占比（最新价×证券数量，行情估值）` |

读取时取「不晚于 `as_of` 的最近一份快照」，**不会**用今天的实时数据顶替历史口径；
超过 7 天标 `stale=true` + `age_days`。同一天已有快照就不重复抓。

### 为什么必须按成分股算

实测同一份快照（2026-11-09）：

| ETF | 名字 | 前三大真实持仓 |
|---|---|---|
| 159529 | 标普**消费**ETF景顺 | `AMZN 13.53% / TSLA 12.82% / WMT 7.83%` |
| 159682 | 创业板50ETF景顺 | 宁德时代 18.89% / 中际旭创 12.48% / 东方财富 7.33% |
| 159586 | 计算机ETF南方 | 科大讯飞 5.47% / 金山办公 4.74% / 同花顺 4.14% |

名字写着"消费"，持仓是美股科技与零售 —— 按名字猜主题会给出**看起来合理但完全
错误**的结论。所以 ETF 的映射证据一律是"当日成分股里哪些命中、合计多少权重"。

### 事件暴露字段（`mapping_evidence`，仅 ETF）

| 字段 | 含义 |
|---|---|
| `observed_at` / `weights_as_of` / `report_period` / `weight_basis` | 口径三件套（见上表） |
| `precise` | 是否拿到了成分股；`false` → 结论只能是"无法精确评估" |
| `matched_weight_pct` / `matched` | **字面命中**的成分股与合计权重（定级只看这部分） |
| `synonym_weight_pct` / `synonym_matched` | 同义词/上下游命中，仅供参考，不参与定级 |
| `affected_weight_pct` / `affected_constituents` | 同一事件下**已判过方向**的成分股及其权重 |
| `by_direction` / `bullish_weight_pct` / `bearish_weight_pct` | 按方向拆开的权重 |
| `unknown_direction_weight_pct` | 判过但方向未定 —— **不并入**利好或利空 |
| `direction_conflict` / `conflict_note` | 同一事件下成分股方向相反时置位，并把提示追加进 `basis` |

实测（159682，用 2026-11-09 真实权重）：

```
2026-11-09 成分股快照中 3 只直接受影响、合计权重 38.7035%
（宁德时代18.892%(利空)、中际旭创12.4846%(利好)、东方财富7.3269%(不确定)）；
其中方向未定 7.3269%；⚠ 成分股方向相反：利好 12.4846%、利空 18.892%
—— 不能当作单一方向的暴露
```

### 三条不许越界的地方

1. **成分数据缺失不退回主题猜测**：`precise=false` + "无法精确评估"，
   不给任何暴露数字（连字段都不出现）。
2. **权重为 0 的持仓不算暴露**：它们存在（新纳入/待调整），但贡献 0，
   统计进去只会让"命中 N 只"虚高。快照里 `constituent_count` 只数权重 > 0 的，
   原始行数另存 `row_count` 与 `zero_weight_count`。
3. **"没受影响"≠"没风险"**：措辞是"已核对当日 N 只成分股，无一直接受该事件影响"。

### 测试与验证

- `databridge/tests/test_etf_exposure.py`（13 项）：快照按天、`as_of` 不越界取历史口径、
  抓取失败标 `precise_ok=false`、过期标 `stale`、同日不重复抓、0% 权重剔除、
  受影响权重求和、方向相反置位并带权重、方向未定不并入利好、无命中措辞、缺快照"无法精确评估"。
- `databridge/tests/test_alert_contract.py` 新增 5 项：口径三件套透传、冲突写进 `basis`、
  跨事件/ETF 同行不参与冲突、方向未定不报冲突、`precise=false` 时不出现暴露字段。
- databridge 全量 **132 passed**；真实 `--dry-run --limit 6` 已落盘
  `data/etf_holdings/2026-11-09.json`（159529 49 行 / 159682 50 行 / 159586 186 行）。
- 核对脚本：`.tspcheck/check_etf_snapshot.py`（打印口径三件套、三大持仓、
  暴露示例、缺数据文案、以及"口径日与文件名是否一致"）。

### 限制

- 权重是**行情估值**，不是基金披露的官方持仓比例；`report_period` 拿不到，
  因此"这是哪一期的持仓"无法回答。
- 事件内方向冲突只统计**同一事件下已判过方向的个股**（多数为"不确定"），
  不代表全市场共识。
- 组合层面仍**未做** ETF → 成分股的行业穿透（账户持有 ETF 时，风险报告里
  仍是 ETF 这一行），见 [组合分析口径](组合分析口径.md) 的已知限制。
