# 模型有效性验证：前瞻跟踪与分组统计

> 起因：「因子目录很丰富」不等于「分析有效」。本模块回答一个可验证的问题 ——
> **我们给出的结论，事后按真实行情算，到底准不准、赚不赚钱**。
> 代码：`backend/app/services/forecast_track.py`、`backend/app/api/track.py`
> 数据：`data/forecast_track/<kind>/<key>/vN.json`（只增不改）

## 一、三个必须分开的概念

很多人把这三件事混成一个"准确率"，于是永远说不清模型有没有用：

| 概念 | 定义 | 分母 |
|---|---|---|
| **方向准确率** | 判「利好」且扣费后上涨、判「利空」且下跌 | 只含**给了明确方向且已打分**的样本 |
| **映射胜率** | 这个「事件→个股」的判断扣费后是否为正收益 | 已打分样本 |
| **证据分层** | 官方证据足/映射明确 vs 推测性主题关联 | 两组分别统计，不合并 |

判「不确定」的样本**不计入方向准确率**——它不是猜错，是拒绝下注。

## 二、防未来信息泄漏的机制

- 每条结论冻结时记录 `as_of`（做判断的日期）与 `data_cutoff`（当时数据可用到哪天），
  且**拒绝** `data_cutoff > as_of`（那等于用未来数据做判断）。
- 评测只读 `data_cutoff` **之后**的行情（`load_close_after`），
  cutoff 当天的价格不进样本。
- 样本不足时**不打分**：`net_return = null` 并计入 `unscored`，
  不会拿 2 天的涨幅冒充 5 天收益。

## 三、只增不改的版本

```
data/forecast_track/event/evtgrp_xxx/
  v1.json   ← as_of=2026-11-08, model_version=v1, payload={...}, evaluations=[...]
  v2.json   ← as_of=2026-11-09, model_version=v2, payload={...}, evaluations=[...]
```

- 重新生成只会得到 `v2`，**v1 永远原样保留**（用户要求：策略变更后不能覆盖旧预测）。
- 评测结果只 `append` 到 `evaluations`，冻结字段（payload / as_of / data_cutoff /
  inputs_fingerprint / model_version）不回头改。
- `inputs_fingerprint` = 输入快照哈希（参数、数据口径），变了就说明口径变了。

## 四、成本与换手

- 扣费口径：买入佣金 `5bp`、卖出佣金 `5bp` + 印花税 `5bp`，合计 **15bp** 计入 `net_return`。
- 换手：一个持有期 = 开仓 1 次 + 平仓 1 次 = `2.0`。写进结果是为了让"换手率"
  有**唯一定义**，避免各页各算一套。
- 同时给出 `max_drawdown`（区间内最大回撤，负值）。

## 五、按市场状态分组

`market_state` **自动**取自 regime 模块已经算好的市场状态
（`regime_builder.load_regime_history`，实际目录 `data/regime_history/part.parquet`，
状态列 `state`），取 `entry_date` 当天或之前最近一天的记录。

不自己另算一套 —— 同一个概念在系统里只能有一个口径。取不到就留 `None`
（该样本不进任何状态分组），**不猜**一个状态。

实测真实取值：

```
2026-10-20 -> lean_strong
2026-11-05 -> strong
2026-11-06 -> weak
2026-11-09 -> weak
```

## 六、接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/track/{kind}` | 冻结一条结论（`event` / `factor`）；再冻一次 = 新版本 |
| GET | `/api/track/{kind}` | 列出已跟踪的结论与版本历史 |
| GET | `/api/track/{kind}/{key}` | 某条结论的全部版本 + 每次评测（核对"旧预测有没有被改写"） |
| GET | `/api/track/{kind}/report` | 补做评测 + 分组报表（方向准确率 / 映射胜率 / 分层） |

`kind` 只允许 `event`（政策事件结论）与 `factor`（因子结论）。

> **刻意不开放给 API Token**：`/api/track` 不在 `api_gateway` 的开放规则表里。
> 冻结是"写"操作，开放出去等于允许外部程序篡改评测基准；读取也属于内部分析口径。

## 八、真实数据上的机制验证（2026-11-09）

用真实 `alerts.jsonl` 与真实 enriched 日线跑通（`.tspcheck/probe_forecast_track.py`，
跟踪记录写临时目录，不污染生产数据）：

```
政策类告警 71 条，其中带事件组且有标的的 7 条
真实日线范围 2024-10-08 ~ 2026-11-06
已冻结 11 条（7 条真实告警 + 4 条回溯样本，后者仅用于验证打分链路）

--- horizon=2 天：成功打分 3 条 ---
方向准确率 1.0   映射胜率 0.6667   平均扣费后收益 +1.03%   最差 -0.82%
平均回撤 -0.22%  换手 2.0
  [官方证据足/映射明确] 已打分 1  方向准确率 1.0
  [推测性主题关联]     已打分 2  方向准确率 1.0

--- horizon=5 天：成功打分 3 条 ---
方向准确率 0.8333  映射胜率 0.8333  平均扣费后收益 +1.58%
  [官方证据足/映射明确] 已打分 2  方向准确率 1.0
  [推测性主题关联]     已打分 4  方向准确率 0.75
```

**这些数字不能当作"模型有效"的证据**：样本只有 3~6 条、其中一半是专门挑出来
验证链路的回溯样本。它证明的是**机制跑通了**，不是结论可信。

真实告警那 7 条**全部落在 `unscored`**，原因是可解释且正确的：

```
cutoff(2026-11-09) 之后只有 0 个交易日，不足 5 天，暂不打分
真实的政策告警都是 11-08/09 产生的，而日线数据只到 11-06
```

这也正是要防的那件事：**没有前瞻数据就不许打分**，而不是拿已有数据凑一个收益。

> 顺带修掉一个真陷阱：跟踪目录与行情目录分离时会读到空目录，报"0 个交易日"，
> 看着像没数据、其实是读错路径。`evaluate()` 因此新增 `price_dir` 参数，
> 并有测试同时钉住"不给就明确说不打分 / 给了就正常打分"两种行为。

## 九、已知限制（如实标注）

1. **样本量目前为 0**：模块刚落地，生产里还没有攒到带前瞻窗口的历史结论
   （真实告警都是 11-08/09 产生的，日线只到 11-06）。报表会显示 `scored: 0`，
   这**不代表**模型有效，也不代表无效。
2. **只有单一持有期**：现在按 `horizon_days` 评一个窗口（默认 5 个交易日），
   没有多周期网格，也没有逐日再平衡。
3. **市场状态自动取，但只在 `/report` 路径上补**：`evaluate()` 本身接受外部传入
   `market_state`；`/api/track/{kind}/report` 会自动按 `entry_date` 从 regime 补齐。
   直接调 `evaluate()` 的离线脚本若需要分组，得自己传。
4. **换手恒为 2**：一个持有期只开平各一次；真正的组合换手要等策略级回测接入。
5. **因子结论尚未自动接入**：`kind="factor"` 的接口已就绪，但还没有把
   因子 IC/分组回测的结论自动 freeze 进来（需要先定义因子的前瞻口径）。
6. **不做统计显著性**：只报命中率与均值，没有置信区间/显著性检验；
   样本少时这些比率本身会剧烈波动。
7. **只有评测是自动的，冻结不是**：`/report` 会自动补评测，但"把结论冻结进来"
   仍需调用 `POST /api/track/{kind}`；目前还没接到告警/因子流水上自动触发。
