## 一、它和政策雷达的分工

| | 处理什么 | 时点 | 能否提前 |
|---|---|---|---|
| `policy_radar.py` | **不知道何时发生**的事件（新闻/公告/政策快讯） | 事后发现 | ❌ 只能事后 |
| **`policy_calendar.py`** | **日期已知**的事件（FOMC/两会/政治局会议/中央经济工作会议） | 提前预警 | ✅ **唯一能真正提前的部分** |

这是这套系统目前**唯一能在事情发生前就给出提示**的模块。

## 二、日期来源与确定性（**核心原则：不编造日期**）

日历文件里**每一条都必须带 `source` 与 `confidence`**，`confidence` 分三档：

| confidence | 含义 | 本次条目 |
|---|---|---|
| `official` | 官方已公布的具体日期，可直接采信 | FOMC 全部会议（美联储官网日程） |
| `convention` | 常年惯例日期，具体待官方公告 | 全国两会（3 月上旬） |
| `estimated` | 按往年规律推算，可能有数天误差 | 中央经济工作会议、政治局会议 |

**当前 13 条**（至 2027-12）：

| 日期 | 事件 | 确定性 |
|---|---|---|
| 2026-12-08~09 | 美联储 FOMC 议息会议 | ✅ 官方 |
| 2026-12-15（估） | 中央经济工作会议 | ⚠️ 推算 |
| 2027-01-26~27 | 美联储 FOMC | ✅ 官方 |
| 2027-03-04（惯） | 全国两会 | ⚠️ 惯例 |
| 2027-04-27~28 / 06-08~09 / 07-27~28 / 09-14~15 / 10-26~27 / 12-07~08 | 美联储 FOMC（含 3 次 SEP） | ✅ 官方 |
| 2027-04-30（估） / 07-30（估） | 中共中央政治局会议 | ⚠️ 推算 |

**FOMC 日程来源：** 美联储官网 <https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm>
（2026 年 8 次、2027 年 8 次，均已公布；决议在第二日）

**注意一个时间口径坑：** FOMC 决议于美东时间第二日 14:00 公布，
**对应北京时间次日凌晨**，A 股的反应通常落在**其后一个交易日**。
日历里已把这一点写进 `note`，避免误判为当日事件。

## 三、提醒节奏

| importance | 提前量 |
|---|---|
| high（FOMC / 两会 / 中央经济工作会议） | **T-7 / T-3 / T-1 / T-0** |
| medium（政治局会议） | T-7 / T-1 / T-0 |

**去重 key = 事件 id + 日期 + 提前量**。
（提前量必须进 key，否则同一事件在 T-7 发过之后，T-1、T-0 就再也发不出来了。）

```
asof=2026-12-09  → [T-0] FOMC 当天（critical）
asof=2026-12-16  → [T-0] 中央经济工作会议进行中（至 12-18）
```

## 四、接入个股分析（已在持仓里体现）

`policy_calendar_soon.json` 存放未来 90 天事件，后端 `_load_calendar()` 取 **45 天内**的
注入个股分析提示词 —— 因为更远的事件对当下判断没有边际价值。

**实测（中国移动 600941.SH，2026-11-04）输出原文：**

> **临近事件（日期确定性标注）**
> - 2026-12-09 美联储 FOMC 议息会议（官方已公布）：涉及汇率、外资流向与大盘风险偏好，
>   对红利类权重品种的相对吸引力存在间接影响，**结果不可预判**。
> - 2026-12-15 中央经济工作会议（**推算日期，需以官方公告为准**）：定调次年经济政策，
>   相关板块含大盘/基建/科技成长，属宏观层面变量。

**它把"确定性"如实带进了结论** —— 官方日期直接采信，推算日期明确标注待确认，
并且没有臆测会议结果。这正是政策日历该有的样子。

## 五、踩坑与设计决定

### 坑 F：`--asof` 调试比空等真实日期高效得多

日历类功能的最大麻烦是"要等到那天才能验证"。
所以脚本内置 `--asof YYYY-MM-DD`，可以直接模拟任意日期验证提醒窗口，
上表四个窗口就是这么测出来的。

### 坑 G：shell 里校验中文子串会失败，别误判为代码 bug

在 pwsh 里用 `"已排定日期的政策/国际事件" in p` 这类判断中文子串，
曾因编码/转义得到 False，但直接打印提示词尾部却能看到内容。
**验证注入是否成功，要看打印出来的正文，不要只信子串断言。**

### 设计决定：为什么单独一个脚本而不是并进 policy_radar

两者的去重逻辑和触发条件本质不同：
- `policy_radar` 按「symbol + 原文标题 + 方向」去重，事件来自滚动新闻；
- `policy_calendar` 按「事件 id + 日期 + 提前量」去重，事件来自静态日历。

硬塞进一个脚本会让两边都难维护。**代价**是多了 1 个定时任务，这个代价可以接受。

## 八、周期型事件（规则生成，避免手写上百条）

除手写的固定事件外，日历支持**规则型周期事件** —— 由脚本按规则展开成具体日期：

| 事件 | 规则 | 确定性 | 依据 |
|---|---|---|---|
| **LPR 报价** | 每月 **20 日 09:00**（遇节假日顺延） | `convention` | 全国银行间同业拆借中心；2024-07-22 起由 9:15 调整为 9:00 |
| **官方制造业 PMI** | **每月最后一日** 09:30 | `convention` | 统计局服务业调查中心 + 中国物流与采购联合会；春节那个月顺延（如 2 月数据于 3-4 发布） |
| **CPI / PPI** | **每月 9~10 日**（窗口） | **`estimated`** | 统计局月度发布 |
| **金融统计数据（社融 / M2）** | **每月 11~15 日窗口**（锚点式，见下） | **`estimated`** | 央行月度发布；实测 2026 年集中在 13~14 日 |

### 关于 CPI/PPI，有一个必须讲清楚的事实

**它没有固定日。** 我把三个不同时期的实际发布日拉出来对照：

| 数据月份 | 实际发布日 |
|---|---|
| 2026 年 9 月 CPI | **10-14** |
| 2026 年 10 月 CPI | **11-03** |
| 2023 年 9 月 PPI | 10-13 |
| 2023 年 10 月 PPI | 11-09 |
| 2026 年 8 月 PPI | 09-09 |

**9 日、13 日、14 日、3 日都出现过。** 所以日历里 CPI/PPI 标的是 `estimated`，
并在条目里明确写着：「**该条目日期是推算，误差可能达数天，请以统计局当月公告为准。
正确用法是「知道月中要出通胀数据」，而不是把 9 日当成确定日**」。

这一条我选择"标注不确定"而不是"给个好看的数字"，因为把推算日当确定日会直接导致误判时点。

### 社融 / M2：同样没有固定日，且窗口更宽

我把 2026 年实际发布日全部拉出来对照：

| 数据期 | 实际发布日 |
|---|---|
| 2026 年 1 月 | 02-13 |
| 2026 年 2 月 | 03-13 |
| 2026 年 Q1 | 04-13 |
| 2026 年 4 月 | 05-14 |
| 2026 年 H1 | 07-15 |
| 2026 年 7 月 | 08-14 |
| 2026 年 8 月 | 09-14 |
| 2026 年 Q3 | 10-14 |

**集中在 11~15 日，偶有 8~9 日**（如 2022-10-11、2025-09-12）。所以标 `estimated`。

**数据口径注意：** 月初发布的是**上一个月**的数据。所以 `instance` 按数据期锚定，
命名也是「2026年10月 · 预计 2026-11-11 前后」。

### 宽窗口必须用"锚点式"，否则一个月生成 5 条重复条目

社融的窗口是 `[11,12,13,14,15]`。如果像 CPI 那样逐日生成，同一次发布会产生 **5 条条目**
（每一条都会各自触发 T-7/T-3/T-1/T-0，用户被刷屏）。

**解法：`anchor: true`** —— 只取窗口内**首个工作日**作为锚点，备注写明窗口范围：

```json
{"id": "shrz_m2", "rule": "monthly_window", "days": [11,12,13,14,15],
 "anchor": true, "data_lag_months": 1, ...}
```

生成效果（每月恰好 1 条）：

```
2026-11-11  estimated  金融统计数据（社融 / M2）（2026年10月 · 预计 2026-11-11 前后）
2026-12-11  estimated  金融统计数据（社融 / M2）（2026年11月 · 预计 2026-12-11 前后）
```

### 已核实的实际日期登记为特例

社融的 8 个已核实发布日已写进 `special_cases.overrides`，命中后 `confidence → official`：

```
2026-09-14  official   金融统计数据（社融 / M2）（2026年8月 · 实际发布 2026-09-14）  ← 特例
2026-10-14  official   金融统计数据（社融 / M2）（2026年9月 · 实际发布 2026-10-14）  ← 特例
2026-11-11  estimated  金融统计数据（社融 / M2）（2026年10月 · 预计 2026-11-11 前后）
```

**注意措辞区分**：推算的写「预计 X 前后」，已核实的写「实际发布 X」。
第一版我把推算锚点也写成"实际发布"，是错的，已修正。

## 九、持仓相关性过滤（**关键设计**）

加了周期事件后，日历条目从 13 条涨到 **69 条**。如果无差别报警，
一个月能刷出十几条噪音（LPR + PMI + CPI × 4 个提前量）。

**所以加了相关性过滤：只有事件的 `affects` 板块与持仓（行业 + 概念）有交集时才报警。**

实测效果（asof=2026-11-04）：

```
日历条目 69 条（固定 + 周期展开）
未来 45 天事件 8 条，其中与持仓相关 6 条

  T-5   CPI/PPI 11月        影响持仓: 标普消费ETF景顺
  T-16  LPR 11月           影响持仓: 东方财富
  T-35  FOMC 12-09         （无持仓命中 → 不报警）
  T-35  CPI/PPI 12月       影响持仓: 标普消费ETF景顺
```

另有**同月周期事件合并**：CPI/PPI 的 9 日与 10 日两个窗口都会各自触发提醒，
按「周期 id + 年月」只保留最早那条，避免同一件事提醒两遍。

### 相关性匹配的两个真实缺陷（已修）

加社融时发现原来有两处**会静默漏报**的问题：

**缺陷 1：同义词不匹配 → 错误跳过**

东方财富的行业标签是「**证券**」，而事件 `affects` 写的是「**券商**」。
两者同义但**没有任何子串重叠**，纯子串匹配判为不相关 ——
结果本该预警的 LPR/社融/FOMC 事件被**静默丢弃**。

修法：加 `SYNONYM_GROUPS`，把券商/证券/非银金融/保险归为一组，
匹配时按同义词组展开。

**缺陷 2：ETF 没有行业标签 → 永远匹配不到**

ETF 不在 `ext_hy_ths`/`ext_gn_ths` 里，只有名称。原来能命中纯属**名称巧合**
（"标普消费ETF"含有"消费"字样），像"券商""算力"这种词就永远匹配不上。

修法：加 `ETF_THEME_KW`，按名称补主题标签：

```
标普消费ETF景顺 → 消费 / 食品饮料 / 家电 / 白酒
计算机ETF南方   → 计算机 / 软件 / 信创 / 算力 / 数据中心 / 人工智能
```

**修复前后的实际差别（asof=2026-11-04）：**

| | 修复前 | 修复后 |
|---|---|---|
| 相关事件数 | 6 条 | **9 条** |
| 社融 T-7 | **漏报** | ✅ 命中东方财富并真实告警 |
| CPI/PPI | 仅靠名称巧合命中"标普消费ETF" | ✅ 正确命中 标普消费ETF + 格力 + 水井坊 |
| FOMC | 漏报 | ✅ 命中东方财富（券商） |

**这是本次最有价值的发现：一个曾经静默生效的漏报缺陷。**
如果不加社融事件，这个缺陷会一直藏着。

## 十四、节假日顺延自动处理（本次新增）

### 为什么必须做

LPR 与 PMI 的规则都写着"遇节假日顺延"，但**中国的工作日不等于周一至周五**：
既有调休（周末上班），也有法定假日（工作日放假）。只按 `weekday()` 判断必然出错。

**实测抓到的两个真实差别：**

| 日期 | 星期 | 直觉判断 | 实际 |
|---|---|---|---|
| **2026-09-20** | **周日** | 非工作日，LPR 应顺延 | **是"中秋节前补班"→ 20 日正常发布** |
| **2026-12-20** | 周日 | 同上 | 非工作日 → **LPR 顺延到 12-21（周一）** |

**如果只按周末规则，2026-09 的 LPR 会被算晚、2026-12 会被算早。**

### 数据来源（三级，按可信度）

新建 `databridge/workday.py`：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `data/work_calendar.json` | 本地缓存，**可人工订正**（最高优先级） |
| 2 | `timor.tech` 节假日 API | 按年取，含"放假"与"调休上班"两类（实测 2026 年 39 条，逐日完整） |
| 3 | `tool_trade_date_hist_sina` | 交易日历兜底，仅有周末信息、无调休 |

### 顺延规则

```
LPR：每月 20 日 → 若 20 日非工作日，顺延到其后第一个工作日
PMI：每月最后一个工作日
```

实测结果：

```
2026-09  LPR→2026-09-20 (调休补班)      ← 若不识别调休会算错
2026-11  LPR→2026-11-20 (工作日)
2026-12  LPR→2026-12-21 (12-20 是周日)
2026-08  PMI→2026-08-31 (工作日)
```

告警文案会把顺延原因写出来，便于核对：

> 每月 20 日，遇节假日顺延：**2026-12-20（周末）→ 2026-12-21**

### 一个重要的降级设计

**国务院通常在上一年 11 月才公布次年放假安排**，所以**次年数据往往取不到**
（实测 2027、2028 现在都是空的，不是接口故障）。

此时脚本：
1. 降级为"仅周末"规则；
2. 把该年所有日期的 `confidence` **从 `convention` 降级为 `estimated`**；
3. 在告警备注里明确写出「**［该年度放假安排尚未公布，日期按周末规则推算］**」。

**宁可标注不确定，也不给一个看起来确定的错日期。**

## 十五、修正一处数据口径错误（PMI）

实现过程中发现原来有个**语义错误**：我原先按月命名成"2026年2月 PMI"，
但 PMI 是**月末发布上一个月的数据** —— 2 月末发布的是 **1 月** PMI。

已修正为在名称里标出数据口径：

```
官方制造业 PMI（2027年2月） · 发布1月数据    ← 2月末发布
官方制造业 PMI（2027年3月） · 发布2月数据
```

并补充说明：**因春节假期影响，2026 年 2 月 PMI 推迟到 3 月 4 日发布**
（数据源：国家统计局 2026 年发布日程表）。

**顺延规则不处理这个例外** —— 它是政策特例，不是节假日顺延，需要人工登记。

## 十六、本次新增后的限制

| 限制 | 说明 |
|---|---|
| **次年放假安排未公布** | 次年的 LPR/PMI 日期按周末规则推算，已降级为 `estimated` 并在告警里注明 |
| **春节那个月的 PMI 是特例** | 顺延规则不覆盖（如 2026-02 PMI 实际 3-4 发布），需人工登记 |
| **CPI/PPI 仍无固定日** | 见第八节，已标 `estimated`；脚本只把落在非工作日的候选剔掉 |
| **未覆盖** | 关税/贸易节点、社融/M2、美联储官员讲话、行业性政策窗口 |
| **无法回测** | 样本仍太少，不能做统计检验 |

| P1 | 关税/贸易节点的维护机制（无固定规则，需人工登记） |
| P2 | 事件后**实际影响记录**（只记录，供日后人工回顾，不做承诺） |

## 十八、人工登记政策特例的机制（本次新增）

### 为什么需要

顺延规则覆盖不了**政策特例**。最典型的是春节月的 PMI：
国家统计局 2026 年发布日程表明确写着「因春节假期影响，2 月份采购经理指数月度报告于 **3 月 4 日**发布」，
而规则按"月末最后一个工作日发布上月数据"会算成 **2026-02-27** —— **提前了 5 天**。

这种例外**规则算不出来，必须人工登记**。

### 数据格式

`data/policy_calendar.json` 新增 `special_cases.overrides`：

```json
{
  "target": "pmi",                    // 必须是 recurring 里已有的 id
  "instance": "2026-02",              // 数据期（不是发布期！）
  "actual_date": "2026-03-04",        // 实际发布日期
  "reason": "……因春节假期影响……",
  "source": "国家统计局《2026年2月中国采购经理指数运行情况》",
  "source_url": "https://www.stats.gov.cn/sj/zxfb/202603/t20260304_1962699.html",
  "verified": "2026-11-04"
}
```

### 关键设计：instance 锚在"数据期"，不是"发布期"

**这是我实现时踩到的坑。** 第一版按**发布月**匹配，结果：

- 2026-02 那份 PMI 在 3 月 4 日发布 → 被当成"3 月实例"
- 于是 override **把 2026-02 的条目删掉了，而不是把它挪到 03-04**
- 结果 **2 月 PMI 直接从日历里消失**

**修正**：统一锚在**数据期**。`instance=2026-02` 表示"2 月的经济活动/2 月 PMI"，
它可能在 2 月末或 3 月初发布 —— 这样标注不会因为日期挪动而对不上。

命名也统一到数据期（中文语境里「2 月 PMI」指的就是 2 月的经济活动）：

```
官方制造业 PMI（2026年1月 · 实际发布 2026-02-28）   ← 规则算出
官方制造业 PMI（2026年2月 · 实际发布 2026-03-04）   ← 特例覆盖，conf=official
```

### 校验（人工登记最容易出错，所以必须校验）

`validate_special_cases()` 逐条检查，**不合法的一律拒用并打印原因**。实测全部拦住：

| 检查项 | 结果 |
|---|---|
| target 不在 recurring 的 id 里 | ✅ 拦住 |
| instance 格式不是 YYYY-MM | ✅ 拦住 |
| actual_date 不是合法日期 | ✅ 拦住 |
| 缺少 source_url / source（未核实不可用） | ✅ 拦住 |
| 同一 (target, instance) 重复登记 | ✅ 报警，后者生效 |
| 实际日期与规则推算日相差 > 40 天 | ✅ 报警（多半填错 instance） |

另有一项**"未匹配"诊断**，且区分两种情况（否则窗口滑过后会天天刷假警报）：

```
[warn] …在展开窗口内但未匹配到条目，请检查 instance 是否写错
[info] …不在本次展开窗口（2026-10-01 ~ 2027-11-30），跳过属正常
```

### 覆盖后的效果

- `confidence` 从 `convention` **提升为 `official`**（人工核实过）
- `note` 写明「［人工登记特例］本实例规则推算 2026-02-28（数据期 2026-02），实际发布 2026-03-04」
- 条目带 `_overridden: true`，便于排查

实测（asof=2026-02-25，春节月）：

```
2026-02-28  T-3   conf=convention  官方制造业 PMI（2026年1月 · 实际发布 2026-02-28）
2026-03-04  T-7   conf=official    官方制造业 PMI（2026年2月 · 实际发布 2026-03-04）  ← 特例生效
```

### 怎么查看与维护

```powershell
# 查看已登记特例 + 校验结果
python policy_calendar.py --cases
```

逐条列出 target / instance / 实际日期 / 核实日期 / 来源 / URL / 原因，以及所有校验问题。

## 十九、本次新增后的限制

| 限制 | 说明 |
|---|---|
| **社融/M2 日期不固定** | 实测 11~15 日窗口为主，偶有 8~9 日；锚点是推算，已标 `estimated` |
| **社融窗口锚点可能早于实际** | 锚点取窗口首日（如 11 日），实际常在 13~14 日，T-7 提醒会略早 |
| **同义词表是人工维护** | 目前 14 组，覆盖常见板块；冷门行业可能仍漏匹配 |
| **特例需人工维护** | 每年放假安排公布后（通常 11 月），需人工核对次年春节月 PMI 等特例 |
| **只支持"改日期"一种特例** | 暂无"取消发布""延期未定"类型（可扩展 `action` 字段） |
| **40 天阈值是启发式** | 跨度超过 40 天会报警，可能误报（如真正的长期改期） |
| **次年放假安排未公布** | 次年 LPR/PMI 按周末规则推算，已降级 `estimated` 并注明 |
| **CPI/PPI 仍无固定日** | 见第八节，已标 `estimated` |
| **未覆盖** | 关税/贸易节点、美联储官员讲话、行业性政策窗口 |
| **无法回测** | 样本仍太少，不能做统计检验 |
