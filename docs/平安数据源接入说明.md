# 平安证券 provider 插件接入说明

**日期**：2026-11-18
**目标**：把平安证券 skill 平台的 ETF 实时快照接成 TSP 的数据源，交给能力路由统一调度。

---

## 一、结论先说

`kline_etf_daily` 的最新分区从 **2026-11-16 推进到 2026-11-18**，3 只持仓 ETF
（159682 / 159586 / 159529）的当日 OHLCV 落库，字段值与平安源逐项一致。

这是通过**新增 `etf` 能力**做到的，不是抢占 `realtime`。

---

## 二、为什么是「新增能力」而不是「复用 realtime」

交接文档 P0 原本写「实现 `get_realtime_symbols` / `get_daily`，把 `realtime_data_provider`
或新开一个 `etf_data_provider` 指过去」。实测后否掉了前两条路：

### 否掉 `get_daily`（不可行）

平安 `klineData` 返回的是**前复权**价，且**无参数可切换**（`adjust=none` / `0` / `nofq`
全部被忽略，响应体 `adjust` 字段恒为「前复权」）。与东财 `fqt=0`（不复权）逐日对比：

| 标的 | 近 180 交易日背离天数 | 最大偏离 |
|---|---|---|
| 600941.SH | 149 / 180 | -4.71 |
| 000651.SZ | 126 / 180 | -5.20 |
| 510300.SH | 除息后当日即背离 | — |
| 600519.SH | 83 / 180 | -1.88 |

内部契约（CONTRIBUTING §3.2）要求日K入库为**不复权原始价**，复权由 `adj_factor` +
`indicators.pipeline` 负责。前复权价进 `kline_etf_daily` 会污染 raw 基准、静默算错复权
因子与全部下游指标 —— 正是「看起来合理但是错的」那类错误。**故日K一列都不取。**

> 快照（`stockDynamic`）的当日 OHLC 是原始价：前复权的锚点是「最新」，当日价恒等于 raw。
> 实测今日 bar 与 quote 逐字段一致，所以快照可安全作为当日值。

### 否掉「复用 realtime」（会打挂股票）

声明 `realtime` 意味着整个全市场轮询周期（含 5583 只股票）都路由给该源。平安单批上限
5 个代码（文档口径，实测 8 个也返回 8 条，但不依赖未公开上限），额度 2000/日 —— 
一轮全市场就要几千次调用。切过去只会让股票整轮空转。

### 采纳：`etf` 独立能力（补拉，不抢轮）

新增能力只做一件事：**补拉本轮全市场快照未覆盖的 ETF**。已覆盖的不重复请求，
额度消耗 = `ceil(未覆盖ETF数 / 5)`。ETF 持仓 3 只时一轮 1 个请求。

## 四、数据契约处理（全部实测，不按字段名推断）

| 平安字段 | 平安原始 | 内部契约 | 处理 |
|---|---|---|---|
| `change_pct` | `"-0.60%"` 字符串 | 小数制 | 剥 `%` → /100 → `-0.006` |
| `turnover_pct` | `"4.88%"` | 小数制 | 剥 `%` → /100 → `0.0488` |
| `volume` | 股 | 手 | `floor(/100)` |
| `amount` / `price` / OHLC | 元 | 元 | 透传 |
| 代码 | `SZ159682` | `159682.SZ` | `to_pa_symbol` / `from_pa_symbol` |

**踩过的三个坑（都已固化为测试）**：

1. **代码格式**：第一版把 `159682.SZ` 直接透传，平安整批判 `not_found`，返回 0 条。
   加 `to_pa_symbol` 转换后正常。
2. **数值是字符串 + `%` 后缀**：`float('0.22%')` 抛 `ValueError`，被 `except` 吞掉后静默变
   `None`。必须先剥后缀。
3. **盘前 0 价**：平安盘前给 `price=0` 且 OHLC 全 0。不回退昨收会让 ETF 显示 0 元、
   0.00% 假跌停。无昨收可退时置 `None`，绝不下发 0 元假价格。

**北交所**：`.BJ` 平安不支持（实测 `not_found`），请求前过滤，避免整批连坐。

## 五、限频与额度

- 实测 0.15s 间隔连打 12 次，有 1 次返回 429（`RATE_LIMIT_EXCEEDED`）。
- 客户端批次间隔 `MIN_INTERVAL_S = 0.35`，429 按 1.2s × 2ⁿ 退避重试 3 次。
- `DAILY_QUOTA_EXCEEDED` 与限流**分开抛**（`PingAnQuotaError` vs `PingAnRateLimitError`），
  额度用尽不白烧退避。
- 额度 2000/日；每批 5 个代码；只补未覆盖标的。

## 七、已知边界（不要误以为已解决）

1. **ETF 换手率不落 enriched 表**。`turnover_rate` 依赖 `float_shares` 股本口径，ETF 全量
   路径不传 `instruments`，属既有架构事实。快照的换手率仍在 provider record 里可取。
2. **历史 ETF 日K缺口仍在**。平台只有前复权序列，补不了 raw 历史。11-16 之前的缺口
   需要另找不复权源。
3. **`etf` 能力不做全市场枚举**。只补持仓/自选里的 ETF。
4. **不做分钟/五档/财务**。平台无对应接口。

# 第二部分：ETF 估值分位（扩展数据表 + 筛选 API）

补的是 `docs/数据缺口清单与优先级.md` 的**缺口 1「历史估值序列（仅快照，无法看分位）」**：
`ext_valuation` 只有当天绝对值，没有「当前处于历史什么位置」。平安 `ETF_FILTER` 直接给
`peFenWei` / `pbFenWei`，一次拿全市场 1721 只。

## 十、接口实测（决定实现方式的四件事）

1. **信封没有 `data` 层**：顶层就是 `{responseCode, currentDate, total, rows}` → `response_path="rows"`。
2. **数值全是字符串**，但单位混杂：分位/涨跌/ROE/费率是**小数**（`peFenWei:"0.0015"` = 0.15%），
   而 `yielD` / `foldingPremiunRates` / `scopeIncreaseM` **已经是百分数**；`scope`、`turnVolume20`
   反而是数字类型。写成「一律 ×100」或「一律原样」都会错一半。
3. **`scope` 与 `turnVolume20` 在源端完全不可筛选**：type 2/3/4/5 全部 `total=0`（字符串值和数字值都试过）。
   `type:8`（数组集合）传 code 数组会被**静默忽略**，返回默认列表而不报错 —— 最坏的一种失败。
   → 因此这两个字段的筛选只能在本地做（见第十三节）。
4. **没有页码参数**，`pageSize` 上限 100。所以全市场枚举只能靠 `code` 游标翻页：
   `wheres=[{field:"code",type:3,value:上一页末个code}]` + `orderBy=code` + `orderType=A`。
   实测 18 页覆盖 1721 只（每页 100 条但首尾 code 重复 → 去重后 new=99，末页 38 条短页结束）。
   **18 次请求/天，额度 2000 完全够；并发上串行（游标天然只能串行），上限 4 未被触碰。**

## 十一、落了什么

- 扩展表 `ext_etf_valuation`（`data/ext_data/ext_etf_valuation/timeseries/date=YYYY-MM-DD/part.parquet`），
  `mode=timeseries`，每交易日 **17:20** 拉一次，1721 行 × 29 列。
- 列：`symbol, code, source_date, name, fund_company, fund_type1, fund_type2, index_name,
  index_code, pe, pb, rsi, scope, amount_20d, favorite_num, search_1w, dividend_yield,
  premium_rate, scope_growth_m, pe_percentile, pb_percentile, roe, cost, rise_5d, rise_20d,
  rise_60d, rise_120d, rise_ytd, rise_1y`。
- **口径**：`pe_percentile` 等分位列是**百分数**（`0.15` 表示 0.15%），与 `cost`/`roe`/涨跌幅一致；
  `pe/pb/rsi` 保持原值，`scope`/`amount_20d` 是元。
- 历史查询不用新写 API：`GET /api/ext-data/ext_etf_valuation/rows`、
  `GET /api/ext-data/ext_etf_valuation/series?field=pe_percentile&symbols=159682.SZ&granularity=daily&days=120`。

## 十二、实时筛选 API

```
GET /api/etf-valuation/screen
  fund_type1=规模宽基|行业主题|...   (逗号多值)
  fund_type2=大盘        index_name=沪深300      code=510300
  pe_max= pe_min= pb_max= pb_min=
  pe_percentile_max=30   pb_percentile_max=20     # 百分数
  dividend_yield_min=3   cost_max=0.5   roe_min=15
  rsi_max= rsi_min=
  order_by=peFenWei|dividend_yield|scope|...   desc=true|false   limit=50(≤100)
```

- 分位/费率/股息/ROE 一律**按百分数传参**（`pe_percentile_max=30` = 分位 ≤ 30%），
  与落库列口径一致，直接对归一后的列比较。
- `order_by` 收**本表列名**（`pe_percentile`/`dividend_yield`）或**源字段名**（`peFenWei`/`yielD`），
  别名表把源名归一到列名；路由前置校验与服务层各校验一次（漏一处就 400）。
- 返回 `total` 是命中总数、`returned` 是本页条数、`cached=true` 表示这一轮没重新翻页 ——
  三者不同，别把 `total` 当返回行数。
- **筛选与排序全部在本地做，源端只负责「按 code 游标翻页」**（理由见第十三节）。
- 列值为空的行不满足任何条件（QDII 无 PE 不会混进「分位 ≤ 30%」），排序时恒排最后。
- `scope_min` / `amount_20d_min` 是本接口独有的能力 —— 源端这两个字段任何操作符都是 0 条，
  只有本地筛选才可用。
- 底层全市场数据在进程内缓存 **180 秒**（一轮 18 次请求，额度 2000/日 撑不住每点一次就全量）。

## 十三、为什么筛选不下发给源端（重要）

源把数值都以**字符串**返回，服务端的比较与排序按**字符串语义**执行，实测三处硬证据：

| 检查 | 服务端口径 | 本地数值口径 | 判定 |
|---|---|---|---|
| `orderBy=pe, orderType=A` 首条 | `10.0823`（515450.SH） | `6.482`（517900.SH） | `"1x" < "6x"`，字符串序 |
| `pe < 20` | 676 | **717** | 差 41 只 |
| `pe<20 且 规模宽基` | 201 | **180** | 服务端 201 **多于**本地 180，筛选用值与返回字段值不同口径 |

分位/费率/股息那几组看起来对得上（742/874/141/517/785）纯属巧合 —— 这些值都是 `0.x` 位数相同，
字符串序恰好等于数值序。**换一批数据就会错，且不报错，只是静默少返/多返行。**

所以最终实现：`walk_universe` 只用来翻页取全市场，`apply_filters` / `_sort_rows` 在归一后的
浮点列上做比较排序。改完用落库 parquet 独立复算做交叉校验，9 组筛选 + 2 组 TopN 全部逐条一致
（`pe_max=20` 从 676 变回 717，最低 PE 首条从 10.0823 变回 6.482）。

## 十四、框架改动：`PullConfig.adapter`（声明式配置表达不了的取数）

有些源的取数形态（按字段游标翻页 + 逐字段归一）无法用 `page_param`/`fanout` 描述。与其在
通用链里堆特例，加了一个**代码级适配器**开关：

```jsonc
"pull": {
  "adapter": { "kind": "pingan_etf_valuation", "page_size": 100, "max_pages": 40 }
}
```

- 登记表在 `backend/app/services/ext_pull.py` 的 `_ADAPTER_KINDS`（`kind` → 模块 + 协程函数）；
- `_fetch_rows_for_date` 优先走 adapter 分支，未知 `kind` 直接报错（不静默退化）；
- **写入 / 分区 / 派生失效 / 查询 API 全部仍走通用链**，adapter 只负责「产出 rows」；
- `since_cursor` 在 adapter 模式下返回 `None`（没有整表游标语义）；
- `PullConfig` 有 `__slots__`，加字段必须四处同改（`__slots__` / `__init__` / `to_dict` / `from_dict`），
  另外 `ext_data_schema.PullConfigReq` 与 `api/ext_data.configure_pull` 要各加一处，
  否则 UI 保存配置时会把 `adapter` 抹掉。

## 十六、已知边界（这些 0 是真 0，不是 bug）

1. **`cost_max=0.15` 返回 0**：全市场最低费率是 0.2%（486 只），没有 ≤0.15% 的产品。
2. **`dividend_yield_min=4 & fund_type1=规模宽基` 返回 0**：宽基股息最高是 3.76%（超大盘ETF博时），
   ≥4% 的 141 只全在风格策略(98)/行业主题(41)/全球市场(2)。
3. **QDII/跨境 ETF 无 PE/PB**：源本身不给，落 `null` 而非 0。
4. **分位为 0 的是新基金**：成立不足一个完整窗口，源给 0（如 530100.SH、560660.SH）。
5. **历史序列要靠每日落库积累**：源只给「当前分位」，没有历史分位接口。表里目前的
   `days=1` 是正常的 —— 缺口 1 从现在开始被逐步填平，不是一次补齐。
6. **不做个股分位**：平安只给 ETF 分位。
7. 额度：落库 18 次/天；筛选首次 18 次、之后 180 秒内命中缓存 0 次（`_universe_cache`）。
   2000/日 余量充足；仍保留 0.35s 级间隔 + 429 退避（`client._post_raw_with_retry`）。

## 十七、回滚

  不会复活 —— 有 `.etf_valuation_seeded` 标记）。

# 第三部分：热股榜单（关注度维度）

TSP 原本**完全没有关注度维度**：行情答「价格怎么动」、`ext_fundflow` 答「钱怎么流」、
`ext_margin` 答「杠杆多少」、龙虎榜答「谁上榜」—— 没有人回答「散户正在看什么」。
热股风向标就补这一块。

## 十八、接口实测（决定实现方式的四件事）

1. **信封是第三套约定**。热股返回 `{status, errmsg, results}`，成功值是 `status == 1`；
   行情是 `code == 0`，金库是 `responseCode == "0"`。三套不能共用判错逻辑 ——
   `client.py` 抽了 `_post_http`（只管 HTTP/JSON 层与限流），业务码由
   `_post` / `_post_raw` / `_post_status` 各判各的。
2. **`time_range` 必须是整数**（1=1h，2=24h）。传 `"1d"` 直接 HTTP 400。
3. **非法取值不报错，静默返回空榜单**。`time_range=3` → `{status:1, total:0, list:[]}`；
   `module_code=nope` → `results` 里连 `list` 都没有。空榜单与参数错误在协议上不可区分，
   所以取值白名单写在 `hot_stock.normalize_*` 里前置拦，不靠上游报错。
4. **`total` 恒为 100**（榜单深度上限，与 `size` 无关）；`size=101` 不报错只回 100 条；
   支持 `page`，但 `size=100` 一次就能拿满 100 名，落库不需要翻页。

条目字段：`chg` 是**小数字符串**（`-0.0999` = -9.99%，落库存百分数）、`cnt` 是热度值整数、
`calcDate` 是 `2026111906`（yyyymmddhh）、`tagList[{name,type,url}]`、
`news{title,newsUrl}`（常常是空串）、`updateTime` 是 `2026-11-19 06:00:00`。
`type_code=block` 时 `marketType` 是 `BI`，`stockCode` 是板块号（994247），不是可交易标的。

## 十九、落了什么（四张表，一榜一张）

| 表 id | 榜单 | 补的是什么 |
|---|---|---|
| `ext_hot_stock` | 热搜榜 `hot_stock` | 用户主动搜索（最强意图） |
| `ext_hot_select` | 加自选榜 `hot_select` | 持续跟踪（用脚投票） |
| `ext_hot_watch` | 浏览榜 `hot_watch` | 看一眼（最弱意图） |
| `ext_hot_surge` | 飙升榜 `hot_surge` | 关注度的**变化速度** |

**为什么必须四张表**：`write_ext_parquet` 的去重键是 `[symbol]`（+ 时间列）。同一只票在四个
榜单里各出现一次，塞进一张表会被去重成一行，只剩最后写的那条。拆表后每张表内 symbol 每日
唯一，跨榜对比靠 `symbol + date` join。

每张表落 **aStock + etf** 两类（各 100 行，合计 200 行/表/日），每日 17:10 收盘后拉取，
四张表合计 8 次请求。`block`/`hkStock`/`bond` 三类**只供即时接口**、不落库：板块已有
`ext_gn_ths`/`ext_hy_ths`，港股与可转债对现有策略无补充。

14 列：`symbol / code / name / market_type / asset_kind / rank / hot_value / chg / tags /
news_title / news_url / calc_date / source_date / updated_at`。

- `rank`：榜单内序位（原始序，跳过的行不压缩名次）；
- `hot_value`：热度值，**同榜同窗口内可比，跨榜/跨窗口不可比** —— 实测加自选 1h 的热度值只有
  300 上下，而热搜 24h 首条是 66249；
- `tags`：`|` 分隔且去重（实测同一条目会重复给「智能家居」）；
- `chg`：百分数（源给小数，已 ×100）。

# 第四部分：研报正文（把评级计数升级成「券商说了什么」）

`ext_research` 现在只有 `buy_cnt/add_cnt/neutral_cnt/reduce_cnt/sell_cnt` 五个计数 ——
知道「有几家给买入」，不知道**理由**。平安研报库提供检索式召回 + 正文片段，
本部分把它接成内置扩展表 `ext_research_note` + 即时检索 API。

## 二十四、接口实测（决定实现方式的五件事）

1. **信封是 `{records, msg}`，HTTP 200 即成功**，没有业务码 —— 这是第四套约定
   （行情 `code==0`、金库 `responseCode=="0"`、热股 `status==1`）。
   `client._post_http` 因此只做 HTTP 层判定，业务码各技能自己解。
2. **必须带平台内置 Bearer token**：`Authorization: Bearer e4c34022e6a64e0d83dfea24b1540415`。
   不带直接 HTTP 500（不是 401），与真故障同码。
3. **`score_threshhold` 是服务端字段名（双 h），但服务端根本不按它过滤**：
   同一 query 传 0.05 与 0.6 返回**完全相同的 44 条**（min 0.25125 / max 0.6674）。
   → 阈值只能在本地做。字段名不许「修正」成 `threshold`。
4. **一条 record 只有 `content / metadata{path,description} / score / title`**。
   没有机构、没有研报类型、没有发布日期。
5. **同一篇研报会被切成多个片段分别返回**（`metadata.path` 里同一个 `id=`）。
   实测 `宁德时代 top_k=30` → 30 片段 / 21 篇，其中一篇有 6 个片段。
   不按文档去重，一张表会被同一篇研报的 4~6 个片段挤满。

## 二十五、为什么不落机构 / 评级 / 发布日期（重要）

这四列在第一版实现里是有的（正则从正文抽），实测 27 篇去重文档后**全部删除**：

| 字段 | 收紧规则后的抽取率 | 实测反例 |
|---|---|---|
| 机构 | 1/27，且那 1 条是错的 | 从「基金代销与证券业务」抽出「基金代销与证券」 |
| 评级 | 0/27 | 「投资评级 \| 」后面是表格分隔行，行内评级才是真的 |
| 发布日期 | 可信的 1/27 | `截至2026年7月31日尚未回购` —— 这是正文数据时点，不是发布日 |

根本原因是**片段是骨架**：27 篇里 30% 不到 200 字，只有「标题 + 核心观点 + 股票代码」；
中位 815 字，p90 3970 字。剩下的长片段多是 markdown 表格（成交榜、融券榜），
不含文档元信息。

结论：**与其给假数据，不如只给片段原文**。表格只保留源端真有的东西 ——
`doc_count / top_score / title / titles / snippet`，要看机构与日期请点开原文
（`doc_id` → `/profile_platform/knowledge-base/5/knowledge/document-detail?id=<doc_id>`）。

回归测试 `test_row_has_no_heuristic_metadata_columns` 专门守这条线：
任何人把 `institution/rating/note_date/date_source` 加回落库列，用例立刻失败。

## 二十六、检索形态（为什么用 6 位代码）

`top_k=20`，`正文命中`＝content 里真的出现该代码/名称：

| 标的 | 形态 | 文档数 | 正文命中 |
|---|---|---|---|
| 000651 格力电器 | **代码** | **15** | **15** |
| | 名称 | 6 | 4 |
| | 名称+代码 | 9 | 9 |
| | 名称+「研报」 | 10 | 9 |
| 300750 宁德时代 | **代码** | **19** | **19** |
| | 名称 | 12 | 12 |
| 601899 紫金矿业 | **代码** | **14** | **14** |

所以 `query_for()` 一律用 6 位代码，非 A 股（港股等）退化为名称。

## 二十七、落了什么

内置扩展表 `ext_research_note`（`mode=timeseries`，**不配 `time_field`**，共 10 列）：

| 列 | 含义 |
|---|---|

# 第五部分：盘中化与开箱预置（把数据变成能用的信号）

前四部分解决「数据进来了」。这部分解决「进来之后怎么用」—— 三个新源接完，
字段确实已自动进了信号白名单（`ext_factors` 把数值型 timeseries 表注册成因子），
但还得手拼条件、而且热股是收盘后才落库，盘中根本用不上。两处都补上了。

## 三十二、热股改成盘中轮询（每盘各存一行）

### 改了什么

```jsonc
// 之前: 每日 17:10 一次
"schedule_time": "17:10", "schedule_period": "daily"
// 现在: 每 30 分钟, 只在交易时段
"schedule_minutes": 30,
"time_window_start": "09:30", "time_window_end": "15:00",
"time_field": "__pull_ts__"        // 保留名: 写入时注入拉取时刻
```

关键在 `time_field`。扩展表的去重键是 `[symbol]` + `time_field`；不配时间列时，
同一票当天多次拉取会被**覆盖成最后一行**，只剩"当前热度"。配了 `__pull_ts__`
之后每盘各存一行，才算得出「热度涨了多少」—— 而增量才是这个维度唯一有价值的信号。

### 顺带修的两个真实缺陷

1. **区间制没有交易日过滤**。`schedule_trading_only` 原先只在固定时刻模式
   （`_is_scheduled_day`）生效，区间制周六日照拉 —— 一天白烧 16 次额度。
   现在抽出 `_interval_skip_reason()`，区间制也过交易日 + 时间窗两道门。
2. **`_in_time_window` 无法注入时刻**。原实现内部硬编码 `cn_now()`，导致
   门禁逻辑无法被单测覆盖。加了可选参数 `now`，并把时区归一（aware → 北京）。

### 三张表怎么收敛回一行

多盘会带来一个副作用：`/rows` 会返回同票的多行。收敛机制是现成的：

- `ext_data.collapse_ext_rows_at(df, at)` —— `at=None` 取末盘，`at="10:00"` 取该时刻
  或之前最近一盘（PIT 安全，不拿后盘伪造前盘）。
- 字段引用可写 `ext_hot_stock.hot_value@10:00` 指定选盘时刻。
- **信号/因子路径自动收敛**：`ext_factors._timeseries_frame` 对
  `(symbol, date)` 做 `keep="last"`，多盘不会 join 扇出，盘中拿到的是最新一盘。

### 迁移是保守的

`_needs_intraday_upgrade()` 只认**出厂形状**（`schedule_time == "17:10"` 且
`schedule_minutes == 1440` 且没有自定义 time_field），三者齐全才升级。
用户改过间隔、改过时刻、或自己配了时间列的，**整份不动** —— 只改一半会得到
既非每日也非盘中的混合配方。

### 代价

4 表 × 2 类 × 每 30 分钟 × 6.5 小时 ≈ **52 次/日**。平安额度 2000/日，占 2.6%。
取数仍串行（`collect_boards` 逐类顺序请求），声明并发上限 4 未被触碰。

## 三十三、开箱预置（`app/services/pingan_presets.py`）

接完数据却要用户自己拼条件，等于没接完。这里把已验证过口径的几条直接播种成
可编辑的定义（幂等，已存在的一律跳过，用户改过的不覆盖）。

### 1) 价格分位因子 `uf_price_percentile_250d`

```
(ts_rank(close, 250) - 1) * 100 / 249      → 0=近一年最低, 100=最高
```

与平安的**估值分位**互补：

| | 算什么 | 覆盖 | 历史 |
|---|---|---|---|
| `ext_etf_valuation_pe_percentile` | PE 在历史上多贵 | 只有 ETF | 从接入日累积 |
| `uf_price_percentile_250d` | 现价在近一年什么位置 | 全标的 | 有完整历史 |

两个都低 = 真便宜；价格低但估值高 = 盈利在崩，是陷阱。

**口径已手工核对**：159682.SZ 在 2026-11-19 的现价于近 250 日中排第 2 位 →
`(2-1)*100/249 = 0.40`，与公式输出一致。窗口不足 250 根时为 null（fail-closed）。

### 2) 四条信号

| id | 条件 | 用途 |
|---|---|---|
| `pa_etf_deep_value` | 估值分位 ≤ 20 **且** 场内折价（`premium_rate < 0`） | 加档买点 |
| `pa_etf_overheated` | 估值分位 ≥ 85 **且** 近一年涨幅 > 30% | 好资产坏价格，减仓 |
| `pa_hot_rising` | 热搜榜前 20（`ext_ext_hot_stock_rank <= 20`） | 关注度上升 |
| `pa_research_new_coverage` | 当日研报 ≥ 2 篇 | 卖方开始覆盖 |

字段名是**双前缀** `ext_ext_*`：`ext_` 是扩展列前缀，配置 id 本身也叫
`ext_etf_valuation`。这是既有约定（`ext_factors.ext_column_name`），不是笔误。

### 3) 四条规则（signal 型，`op="truth"` 引用上面的信号列）

标的清单 = 播种时的**持仓 ∪ 自选快照**。想跟着自选分组动态走，把 `scope`
改成 `watchlist_group` 并选分组即可（`_apply_scope` 每轮实时解析成员）。

### 刻意没播种的两条

- **「热度跃升」规则**：`hot_value` 的跨期增量还没有历史数据验证方向（顺势还是
  反向未知）。等落够 2–4 周、回测出方向再定阈值 —— 现在写任何阈值都是猜的。
- **个股估值分位信号**：`ext_valuation` 只有 11 个分区，算不出 3 年分位；平安的
  估值分位只覆盖 ETF。

### 一个必须记住的顺序坑

预置播种排在 `load_runtime_registry()` **之后**（要等基础信号与因子先入表），
所以写因子文件后必须**立即 `register_definition()`** —— 只写文件的话，当次启动
注册表里没有它，引用该因子的信号会报缺列，要等下次重启才自愈。已加回归用例
`test_seed_factor_registers_immediately` 守这条。

## 三十五、盘中多盘的已知边界

1. **平安额度当天被用尽时无法验证多盘**（实测遇到 HTTP 429 `DAILY_QUOTA_EXCEEDED`）。
   落库逻辑与收敛逻辑都有单测覆盖，但「盘中真的落下多盘」需要等额度恢复后看
   `/api/ext-data/ext_hot_stock/rows` 的 `total` 是否 > 单盘 200。
2. **同一天多盘不改变 `hot_value` 的可比范围**：仍是「同榜同窗口内可比」，
   跨榜不可比（热搜 top1 六位数，加自选 top1 三位数）。
3. **法定节假日无法离线判定**，与既有固定时刻模式同口径：照尝试、拉取幂等。
